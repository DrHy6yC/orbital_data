# Orbital Data Platform

Учебный Data Engineering-проект: платформа для сбора, хранения, обработки и анализа данных об искусственных спутниках и других орбитальных объектах.

## 1. Цель проекта

Разработать платформу, которая получает данные из нескольких источников, сохраняет их оригиналы, обрабатывает и предоставляет для аналитики.

Основные задачи:

- Сбор данных из независимых источников.
- Сохранение оригинальных данных и истории их изменений.
- Организация хранения обработанных данных.
- Проверка качества и сопоставление данных из разных источников.
- Построение аналитических витрин.
- Автоматизация процессов сбора и обработки.
- Предоставление данных через REST API.

Проект также служит практической площадкой для изучения Data Engineering и связанных технологий.

## 2. Текущий статус проекта

На данный момент реализованы:

- HTTP-клиенты для CelesTrak и Space-Track.
- Загрузка пяти выбранных наборов данных.
- Обработка ошибок, ограничений источников и временных сбоев.
- Сохранение оригинальных ответов в локальном каталоге `data/`.
- PostgreSQL для хранения метаданных и операционной информации.
- RustFS — основное объектное хранилище для исходных данных.
- MinIO — локальная копия объектного хранилища.
- Выгрузка исходных снимков в Bronze RustFS.
- Копирование данных из RustFS в MinIO.
- Скрипт резервного копирования в Yandex Object Storage.

**Текущий этап:** организация хранилища данных. Резервное копирование во внешнее облако находится в работе. Формирование слоя Silver и аналитическая обработка ещё не реализованы.

Подробный статус разработки: [PLAN.md](PLAN.md).

## 3. Архитектура данных

Платформа использует архитектуру Lakehouse — подход к организации данных, объединяющий хранение исходных файлов и аналитическую обработку.

Данные разделяются на три слоя:

| Слой | Назначение |
|---|---|
| **Bronze** | Исходные данные, полученные от источников и сохранённые без изменений. |
| **Silver** | Обработанные, нормализованные и проверенные данные в формате Parquet. |
| **Gold** | Аналитические наборы данных и витрины, подготовленные для запросов и анализа. |

Основные правила хранения:

- Оригиналы данных не изменяются при обработке.
- Каждый новый снимок сохраняется отдельно, что позволяет отслеживать историю изменений.
- Bronze и Silver хранятся в S3-совместимых объектных хранилищах.
- Gold хранится в ClickHouse, а не в S3.
- PostgreSQL используется для хранения метаданных: информации об источниках, загрузках, снимках и их копиях.

**Роли хранилищ:**

- **RustFS** — основное S3-хранилище для Bronze и Silver.
- **MinIO** — локальная копия Bronze и Silver.
- **Yandex Object Storage** — внешнее резервное хранилище.

Подробная схема хранения, правила именования объектов и порядок восстановления: [storage.md](docs/storage.md).

## 4. Источники данных

Платформа использует два основных источника:

| Источник | Назначение |
|---|---|
| [CelesTrak](https://celestrak.org/) | Получение орбитальных данных GP и SupGP в форматах TLE и OMM. Доступ открыт. |
| [Space-Track](https://www.space-track.org/) | Получение GP, GP_History, SATCAT и DECAY. Требуется регистрация. |

TLE и OMM — форматы представления орбитальных параметров объектов.

Перечень источников, выбранные наборы данных, способы получения и ограничения описаны в документации:

- [Каталог источников](docs/catalog.md) — перечень источников и подробности по каждому из них.
- [Выбранные наборы данных](docs/datasets.md).

## 7. Установка и запуск

Инструкции рассчитаны на macOS, Linux и Windows. Для Windows используются команды PowerShell.

### 7.1. Требования

Перед началом работы необходимо установить:

- Python 3.12 или новее — выполнение Python-кода.
- uv — управление зависимостями и виртуальным окружением.
- Git — получение исходного кода проекта.
- Docker с поддержкой `docker compose` (на Windows и macOS — Docker Desktop) — запуск PostgreSQL и RustFS.
- Go 1.24 или новее — только для локального запуска MinIO.

### 7.2. Получение проекта

Клонировать репозиторий:

```bash
git clone https://github.com/DrHy6yC/orbital_data.git
cd orbital_data
```

### 7.3. Установка зависимостей

Установить зависимости проекта:

```bash
uv sync
```

Команда создаст виртуальное окружение и установит необходимые зависимости согласно `pyproject.toml` и `uv.lock`.

### 7.4. Настройка окружения

Создать файл `.env` на основе образца.

macOS / Linux:

```bash
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Заполнить необходимые настройки:

- Учётные данные Space-Track.
- Пароли PostgreSQL и RustFS.
- Параметры подключения к MinIO.
- Учётные данные Yandex Object Storage.

Для получения данных CelesTrak регистрация не требуется.

Скрипты читают этот файл через ключ `--env-file .env`, поэтому команды ниже запускаются из корня проекта. Файл `.env` содержит конфиденциальные настройки и не должен попадать в Git.

### 7.5. Настройка доступа к Space-Track

Для работы с Space-Track необходима бесплатная регистрация:

https://www.space-track.org/auth/createAccount

После регистрации необходимо подтвердить электронную почту и указать учётные данные в `.env`.

### 7.6. Запуск PostgreSQL и RustFS

PostgreSQL и RustFS работают в Docker. В `docker-compose.yml` сервис RustFS называется `s3`.

Запустить основные сервисы:

```bash
docker compose up -d postgres s3
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

Оба контейнера должны быть в состоянии `healthy`. Если указано `starting`, подождите несколько секунд и повторите команду.

RustFS доступен по адресам из `.env`:

| Что | Адрес по умолчанию |
|---|---|
| S3 API | http://localhost:9000 |
| Веб-консоль | http://localhost:9001 |

Вход в консоль — по `S3_RUSTFS_ACCESS_KEY` и `S3_RUSTFS_SECRET_KEY`. Консоль слушает только `127.0.0.1` и снаружи машины недоступна.

Данные RustFS хранятся в томе Docker `s3-data`, данные PostgreSQL — в каталоге `postgres-data/`. Оба места в Git не попадают. Команда `docker compose down -v` удаляет том `s3-data` вместе со всеми объектами: после этого Bronze восстанавливается только из MinIO (7.12) или из Yandex.

Бакеты `bronze` и `silver` создаются автоматически при проверке хранилищ (7.9), отдельная команда для этого не нужна.

### 7.7. Создание схемы PostgreSQL

Применить SQL-файлы проекта:

```bash
uv run --env-file .env python utils/apply_sql.py sql
```

Скрипт создаёт необходимые таблицы и справочники PostgreSQL. Файлы применяются по порядку в одной транзакции: ошибка в любом из них откатывает всю пачку.

`sql/001_schema.sql` не идемпотентен: на существующей схеме он упадёт. `sql/002_seed.sql` заполняет справочники и повторный запуск переносит спокойно.

Если схему нужно создать заново (удаляет данные метаданных, но не саму базу):

```bash
docker compose exec -T postgres psql -U orbital -d orbital_data -c "DROP SCHEMA IF EXISTS orbital CASCADE;"
uv run --env-file .env python utils/apply_sql.py sql
```

Содержимое таблиц удобнее проверять в DBeaver: консоль Windows искажает кириллицу.

### 7.8. Запуск MinIO

MinIO используется как локальная копия основного объектного хранилища.

Инструкция по установке и настройке: [MINIO_INSTALL_LOCAL.md](MINIO_INSTALL_LOCAL.md).

После установки запустить MinIO из корня проекта.

macOS / Linux:

```bash
chmod +x utils/run_minio.sh
./utils/run_minio.sh
```

Windows PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File utils\run_minio.ps1
```

MinIO работает, пока открыто окно терминала, данные хранятся в `storage/minio`.

### 7.9. Проверка хранилищ

Проверить подключение, создание бакетов и операции записи и чтения:

```bash
uv run --env-file .env python utils/check_s3.py
```

Посмотреть бакеты и объекты, ничего не записывая и не удаляя:

```bash
uv run --env-file .env python utils/check_s3.py --list
```

### 7.10. Проверка подключения к источникам

Проверить доступность CelesTrak и Space-Track:

```bash
uv run --env-file .env python utils/check_connection.py
```

Скрипт делает по одному запросу к каждому источнику. Эти запросы расходуют окно частоты, поэтому при отладке учитывайте ограничения из 7.11 и не запускайте проверку подряд.

### 7.11. Загрузка данных

Запустить загрузку выбранных наборов:

```bash
uv run --env-file .env python utils/check_download.py
```

Скрипт получает данные из источников, сохраняет оригиналы в `data/` и выгружает снимки в Bronze RustFS. Для каждого набора печатаются размер, путь к файлу и ключ объекта в бакете.

Источники ограничивают частоту запросов на учётную запись:

| Источник | Наборы | Не чаще |
|---|---|---|
| CelesTrak | `gp_stations`, `gp_active` | одного раза в 2 часа на каждый набор |
| Space-Track | `gp` | одного раза в час |
| Space-Track | `satcat`, `decay` | одного раза в сутки |

Полный прогон занимает около 152 МБ и несколько минут. Если запустить загрузку раньше разрешённого интервала, источник вернёт ошибку, а скрипт завершится с кодом 1. Повторять запрос сразу бесполезно: нужно дождаться окна. По этой причине загрузку не запускают многократно при отладке — для проверки кода служат тесты (8.1).

Ошибка выгрузки в Bronze не удаляет локальный файл и не мешает загрузить остальные наборы: в отчёте она появится строкой `upload:<набор>`.

### 7.12. Дублирование данных в MinIO

MinIO должен быть запущен (7.8). Скопировать Bronze и Silver из RustFS в MinIO:

```bash
uv run --env-file .env python utils/sync_storage.py --dry-run
uv run --env-file .env python utils/sync_storage.py
```

`--dry-run` показывает план без записи. Копируются отсутствующие объекты и объекты с отличающимся размером, в MinIO ничего не удаляется. Повторный запуск ничего не копирует. Ключ `--bucket bronze` ограничивает работу одним бакетом.

### 7.13. Резервное копирование в Yandex

Скрипт находится в работе (подэтап 4.6): проверка доступа и пробный запуск без загрузки готовы, сжатие и окна хранения ещё не сделаны.

```bash
uv run --env-file .env python utils/backup_to_cloud.py --check
uv run --env-file .env python utils/backup_to_cloud.py --dry-run
```

Ключ `--only bronze` или `--only postgres` ограничивает работу одной частью.

## 8. Проверка и тестирование

### 8.1. Автоматические тесты

Запустить тесты:

```bash
uv run pytest
```

Тесты не обращаются ни к источникам, ни к объектным хранилищам. HTTP-клиенты работают на `httpx.MockTransport` — механизме имитации HTTP-ответов, а S3-клиенты заменены объектами в памяти. Проверяются разбор ответов, обработка ошибок и ограничений источников, сохранение снимков, выгрузка в Bronze и копирование между хранилищами.

### 8.2. Проверка качества кода

Проверить форматирование:

```bash
uv run ruff format --check .
```

Проверить код с помощью линтера:

```bash
uv run ruff check .
```

### 8.3. Живая проверка загрузки

Для проверки взаимодействия с реальными источниками используется команда из 7.11. Учитывайте ограничения частоты: CelesTrak — раз в 2 часа на набор, Space-Track `GP` — раз в час, `SATCAT` и `DECAY` — раз в сутки. Повторный запрос раньше окна завершится ошибкой.
