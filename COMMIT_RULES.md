# Правила коммитов

## 1. Общие правила

- Один коммит — одно логическое изменение.
- Нельзя смешивать новые возможности, переработку кода и исправления форматирования.
- Весь текст коммита пишется на русском языке, включая тип и область.
- В описательной части не использовать кальки и англицизмы: «фикс», «мерж», «рефакторинг», «деплой». Использовать русские варианты: «исправление», «слияние», «переработка», «выкладка».
- Английские слова допустимы в трёх случаях:
  - названия из кода: файлы, папки, функции, переменные, таблицы;
  - команды и технические идентификаторы: `git reset`, `git revert`, `api`, `sql`;
  - общепринятые термины, для которых нет устоявшегося русского эквивалента.

## 2. Формат коммита

```text
тип(область): что сделано

Почему: причина или цель изменения.

Файлы:
- путь/к/файлу: что изменено
- путь/к/файлу: что изменено
```

Блоки `Почему:` и `Файлы:` необязательны.

### 2.1. Заголовок

Заголовок отвечает на вопрос **«Что сделано?»** и описывает выполненную работу, а не причину её выполнения.

Требования:
- Описание формулируется в прошедшем времени: «добавил», «создал», «исправил», «удалил», «реализовал».
- Не использовать неопределённую форму глагола: «добавить», «создать», «исправить».
- В конце заголовка не ставится точка.
- При создании файла необходимо указывать его назначение.
- Не использовать общие формулировки без пояснения: «добавил файлы», «улучшил код», «обновил проект».

### 2.2. Причина изменения

Блок `Почему:` добавляется, если из заголовка и контекста изменений не очевидно, зачем они нужны.

Причина должна:
- объяснять цель изменения;
- быть отделена от описания выполненной работы;
- не повторять заголовок другими словами.

### 2.3. Затронутые файлы

Блок `Файлы:` содержит список затронутых файлов. Для каждого файла указывается путь и краткое описание того, что в нём изменено.

## 3. Типы коммитов

### 3.1. Таблица типов

| Тип | Когда использовать | Пример |
|---|---|---|
| новое | Добавление новой возможности | `новое(загрузка): добавил загрузчик данных о спутниках` |
| исправление | Исправление ошибки в поведении | `исправление(аналитика): исправил расчёт суммы заказа` |
| документация | Изменение документации и комментариев | `документация(источники): описал формат входного файла` |
| стиль | Форматирование без изменения логики | `стиль(обработка): привёл имена функций к PEP 8` |
| переработка | Изменение структуры без смены поведения | `переработка(загрузка): разделил функцию загрузки` |
| ускорение | Оптимизация времени или памяти | `ускорение(аналитика): оптимизировал запрос расчёта` |
| тесты | Добавление или изменение тестов | `тесты(загрузка): добавил тест на пустой файл` |
| сборка | Зависимости и сборка проекта | `сборка(зависимости): добавил библиотеку pyarrow` |
| автоматизация | Автоматические проверки и запуск | `автоматизация(тесты): добавил запуск тестов` |
| прочее | Служебные изменения, не подходящие под другие типы | `прочее(настройки): добавил правила коммитов` |
| откат | Отмена предыдущего коммита | `откат(загрузка): отменил изменение формата файла` |

### 3.2. Как выбрать тип

- Изменилось поведение для пользователя или данных — `новое` или `исправление`.
- Поведение прежнее, изменилась структура кода — `переработка`.
- Изменилось только форматирование — `стиль`.
- Изменилось только время выполнения или потребление памяти — `ускорение`.
- Изменилась только документация — `документация`.
- Изменились только тесты — `тесты`.
- Изменились зависимости или настройки сборки — `сборка`.
- Изменились автоматические проверки — `автоматизация`.
- Изменение не подходит под остальные типы — `прочее`.
- Отменяется ранее сделанный коммит — `откат`.

## 4. Область коммита

Область указывается в круглых скобках после типа и отвечает на вопрос: **«Какой части проекта касается изменение?»**

### 4.1. Правила выбора

1. Использовать короткое название функциональной части проекта.
2. Предпочитать русские названия; английские (`api`, `sql`) допустимы только как общепринятые термины.
3. Указывать основную область, в которой выполнено изменение.
4. Не указывать название отдельного файла, если изменение относится к более широкой части проекта.
5. Не использовать область для повторения типа коммита.
6. Если изменение затрагивает несколько независимых областей, разделить его на отдельные коммиты.
7. Если изменение относится ко всему проекту и не имеет более конкретной области, использовать `проект`.

### 4.2. Допустимые области

| Область | Когда использовать |
|---|---|
| проект | Общая структура, README, план, бэклог и правила проекта |
| источники | Документация и взаимодействие с источниками данных |
| загрузка | Получение данных из внешних источников |
| хранение | Сохранение исходных и обработанных данных |
| обработка | Парсинг, преобразование и нормализация данных |
| аналитика | SQL-модели, расчёты и аналитические витрины |
| api | Методы и логика API |
| тесты | Общие тестовые инструменты и инфраструктура тестирования |
| настройки | Конфигурация и параметры проекта |
| зависимости | Библиотеки и управление зависимостями |
| структура | Организация каталогов и расположение файлов |
| утилиты | Вспомогательные скрипты и инструменты |

## 5. Несовместимые изменения

Если изменение нарушает обратную совместимость:

1. добавить `!` после области в заголовке;
2. добавить в тело строку `ВАЖНО:` с описанием необходимых действий.

Пример:

```text
новое(загрузка)!: добавил поле времени получения в формат заказов

Почему: необходимо сохранять время получения данных отдельно от времени создания заказа.

ВАЖНО: перед запуском выполнить миграцию базы данных.

Файлы:
- src/load_orders.py: добавил чтение нового поля
- migrations/0003_add_received_at.py: добавил колонку времени получения
```

## 6. Примеры коммитов

### 6.1. Хорошо

- `документация(источники): описал подключение к CelesTrak`
- `новое(загрузка): добавил получение орбитальных данных`
- `переработка(структура): перенёс вспомогательный скрипт в утилиты`
- `документация(проект): обновил план и бэклог разработки`
- `сборка(зависимости): добавил библиотеку pyarrow`

### 6.2. Плохо

- `документация(файлы): описал источники данных` — слишком общая область.
- `новое(новое): добавил загрузчик данных` — область повторяет тип.
- `переработка(celestrak.py): изменил структуру загрузчика` — указано имя файла вместо функциональной области.
- `документация(загрузка): описал структуру каталогов` — область не соответствует содержанию изменения.
- `новое(загрузка): добавил файл загрузки данных` — общая формулировка без пояснения назначения.

### 6.3. Полное сообщение

```text
новое(загрузка): добавил загрузчик данных о спутниках

Почему: требуется автоматизировать получение актуальных орбитальных данных из CelesTrak и сохранить их для последующей обработки.

Файлы:
- src/orbital_data_platform/collectors/celestrak.py: добавил загрузчик данных из CelesTrak
- tests/test_celestrak.py: добавил тесты проверки загрузчика
```

Заголовок отвечает на вопрос «Что сделано?», блок `Почему` — «Зачем это сделано?», список в конце — «Какие файлы затронуты?».

## 7. Проверка заголовка хуком

### 7.1. Что проверяет хук

Хук `commit-msg` проверяет заголовок перед созданием коммита:
- допустимый тип;
- наличие области в круглых скобках;
- формат `тип(область): описание`;
- минимальную длину описания (3 символа).

Хук **не** проверяет область на соответствие таблице 4.2 — это осознанное решение, чтобы позволять расширять список областей без правки хука. Согласованность области с таблицей контролируется на ревью.

### 7.2. Расположение файлов

Хуки подключаются к конкретному проекту копированием в `.git/hooks/`. Исходники могут храниться централизованно и копироваться в нужный проект.

Исходники (Windows):

```text
$HOME\.git-hooks\
├── commit-msg
└── check_commit_message.py
```

Исходники (Linux/macOS):

```text
~/.git-hooks/
├── commit-msg
└── check_commit_message.py
```

Подключённые хуки в проекте:

```text
.git/hooks/
├── commit-msg
└── check_commit_message.py
```

### 7.3. Код хука

`check_commit_message.py`:

```python
import re
import sys

ALLOWED_TYPES = (
    "новое|исправление|документация|стиль|переработка|ускорение|"
    "тесты|сборка|автоматизация|прочее|откат"
)
HEADER_PATTERN = rf"^({ALLOWED_TYPES})\([\w-]+\)!?: .{{3,}}$"
# MAX_HEADER_LENGTH = 72  # если нужно ограничить длину заголовка

with open(sys.argv[1], encoding="utf-8") as message_file:
    header = message_file.readline().rstrip("\r\n")

if not re.match(HEADER_PATTERN, header):
    print("Неверный заголовок коммита.")
    print("Формат: тип(область): описание")
    print("Пример: исправление(аналитика): исправил расчёт суммы заказа")
    print("Типы: " + ", ".join(ALLOWED_TYPES.split("|")))
    sys.exit(1)

# если нужно ограничить длину заголовка
# if len(header) > MAX_HEADER_LENGTH:
#     print(f"Заголовок длиннее {MAX_HEADER_LENGTH} символов.")
#     sys.exit(1)
```

`commit-msg` — POSIX sh-скрипт (запускается через `sh`, в том числе встроенный в Git for Windows):

```sh
#!/bin/sh
python "$(dirname "$0")/check_commit_message.py" "$1"
```

Требования к окружению:
- Python доступен в `PATH` как `python` (при необходимости заменить на `python3`);
- `check_commit_message.py` сохранён в UTF-8 без BOM;
- `commit-msg` сохранён с окончаниями строк LF.

### 7.4. Установка и проверка

Команды даны для PowerShell; в bash/macOS/Linux используются эквиваленты (`cp`, `mv`).

Проверка отклонения неверного заголовка (при установленном хуке):

```powershell
git commit --allow-empty -m "что-то сделал"
```

Проверка прохождения правильного заголовка:

```powershell
git commit --allow-empty -m "прочее(настройки): проверил работу хука"
```

Пробные коммиты удалять только в том случае, если они действительно созданы специально для проверки. Для пустого пробного коммита на чистой рабочей директории:

```powershell
git reset --hard HEAD~1
```

**Внимание:** `git reset --hard` удаляет не только последний коммит, но и все незакоммиченные изменения. Применять только для пробных коммитов на чистой рабочей директории.

### 7.5. Изменение и отключение хука

Правила меняются в **исходнике** `$HOME\.git-hooks\check_commit_message.py` (Linux/macOS — `~/.git-hooks/check_commit_message.py`). После правки файл нужно заново скопировать в `.git/hooks/` проекта. Правка копии в `.git/hooks/` допустима для разовой проверки, но при следующей переустановке изменение будет потеряно.

Для добавления нового типа необходимо изменить `ALLOWED_TYPES` и синхронизировать таблицу 3.1.

Временно отключить проверку (PowerShell):

```powershell
Rename-Item ".git\hooks\commit-msg" "commit-msg.off"
```

Включить обратно (PowerShell):

```powershell
Rename-Item ".git\hooks\commit-msg.off" "commit-msg"
```

Эквивалент для bash/macOS/Linux:

```bash
mv .git/hooks/commit-msg .git/hooks/commit-msg.off
mv .git/hooks/commit-msg.off .git/hooks/commit-msg
```

Пропустить проверку один раз (файл `COMMIT_MSG.txt` должен существовать и содержать сообщение):

```powershell
git commit --no-verify -F COMMIT_MSG.txt
```

Пропуск использовать только при обоснованной необходимости.

## Приложение A. Шпаргалка по git

Команды сгруппированы по темам. Примеры даны для PowerShell; синтаксис совместим с bash/macOS/Linux, кроме случаев, отмеченных отдельно.

### A.1. Просмотр истории и состояния

```powershell
# Полная история
git log

# Краткая история
git log --oneline

# Последние 5 коммитов
git log -5 --oneline

# История с графом веток
git log --oneline --graph --all

# Последний коммит целиком
git log -1

# Тема (subject) последнего коммита
git log -1 --format=%s

# Содержимое и метаданные последнего коммита
git show HEAD

# Статистика изменений последнего коммита (файлы и строки)
git show --stat HEAD

# Состояние рабочей директории
git status
```

### A.2. Отмена и удаление коммитов

`HEAD~N` означает «на N коммитов назад». `git reset --mixed` — режим по умолчанию.

```powershell
# Удалить последний коммит, оставив изменения в индексе
git reset --soft HEAD~1

# Удалить последний коммит, оставив изменения в файлах (режим по умолчанию)
git reset --mixed HEAD~1

# Удалить последний коммит вместе с изменениями
git reset --hard HEAD~1

# Удалить последние N коммитов с сохранением изменений в индексе
git reset --soft HEAD~N

# Удалить последние N коммитов вместе с изменениями
git reset --hard HEAD~N
```

Удаление конкретного коммита через интерактивное изменение истории:

```powershell
git rebase -i HEAD~5
```

В открывшемся списке заменить `pick` на `drop` для коммитов, которые нужно удалить.

Отмена коммита новым коммитом (без переписывания истории):

```powershell
# Отменить последний коммит
git revert HEAD

# Отменить конкретный коммит
git revert <commit_hash>
```

Для уже опубликованных коммитов предпочтительно использовать `git revert`, чтобы не переписывать общую историю.

### A.3. Восстановление коммитов

```powershell
# Посмотреть историю перемещений HEAD
git reflog
```

После `git reflog` восстановление на нужное состояние выполняется командой `git reset --hard <commit_hash>` (см. A.2). Команда `reset --hard` удаляет незакоммиченные изменения — перед её использованием необходимо проверить состояние рабочей директории.

### A.4. Работа с удалёнными репозиториями

```powershell
# Отправить изменения
git push

# Принудительно отправить с проверкой, что удалённая ветка не менялась после последнего fetch
git push --force-with-lease

# Получить сведения об удалённом репозитории без слияния
git fetch

# Посмотреть удалённые ветки
git branch -r
```

Настройка двух удалённых репозиториев (GitHub и GitLab) и общего алиаса `all` для одновременной отправки:

```powershell
# Основной удалённый репозиторий GitHub
git remote add origin https://github.com/DrHy6yC/orbital_data.git

# Второй удалённый репозиторий GitLab
git remote add gitlab https://gitlab.com/drhy6yc/orbital_data.git

# Алиас all с первым адресом (GitHub)
git remote add all https://github.com/DrHy6yC/orbital_data.git

# Добавить в алиас all второй адрес (GitLab) для отправки
git remote set-url --add all https://gitlab.com/drhy6yc/orbital_data.git

# Отправить ветку main сразу на GitHub и GitLab
git push all main
```
