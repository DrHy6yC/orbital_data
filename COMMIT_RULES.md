# Правила коммитов

## 1. Общие правила

- Один коммит — одно логическое изменение.
- Нельзя смешивать новые возможности, переработку кода и исправления форматирования.
- Если изменения относятся к разным задачам, коммиты необходимо разделить.
- Весь текст коммита пишется на русском языке, включая тип и область.
- Английские слова допустимы только в названиях из кода: файлы, папки, функции, переменные, таблицы и команды.
- Не использовать кальки и англицизмы: «фикс», «мерж», «рефакторинг», «деплой».
- Использовать русские варианты: «исправление», «слияние», «переработка», «выкладка».

## 2. Формат коммита

```text
тип(область): что сделано

Почему: причина или цель изменения (необязательно).

Файлы:
- путь/к/файлу: что изменено
- путь/к/файлу: что изменено
```

### Заголовок

Заголовок обязательно отвечает на вопрос **«Что сделано?»**.

Требования:
- Длина — не более 72 символов.
- Описание формулируется в прошедшем времени: «добавил», «создал», «исправил», «удалил», «реализовал».
- Не использовать неопределённую форму глагола: «добавить», «создать», «исправить».
- В конце заголовка не ставится точка.
- Заголовок описывает выполненную работу, а не причину её выполнения.
- При создании файла необходимо указывать его назначение.
- Не использовать общие формулировки без пояснения: «добавил файлы», «улучшил код», «обновил проект».

### Причина изменения

Блок `Почему:` необязателен.

Его следует добавлять, если из заголовка и контекста изменений не очевидно, зачем они нужны.

Причина должна:
- объяснять цель изменения;
- быть отделена от описания выполненной работы;
- не повторять заголовок другими словами.

### Затронутые файлы

В конце сообщения обязательно указывается список затронутых файлов.

Для каждого файла указывается путь и краткое описание того, что в нём изменено.

## 3. Примеры коммитов

### Добавление новых файлов

Хорошо:

```text
новое(загрузка): добавил файл загрузки данных о спутниках
```

Плохо:

```text
новое(загрузка): добавить файл загрузки данных о спутниках
```

Плохо:

```text
новое(загрузка): добавил файлы
```

### Добавление функциональности

```text
новое(загрузка): реализовал получение данных о спутниках из CelesTrak
```

### Исправление ошибки

```text
исправление(sql): исправил расчёт количества спутников на орбите
```

### Переработка кода

```text
переработка(загрузка): разделил загрузку и проверку данных
```

### Добавление тестов

```text
тесты(загрузка): добавил проверку обработки пустого ответа источника
```

### Изменение документации

```text
документация(проект): описал структуру каталогов проекта
```

### Полное сообщение с причиной

```text
новое(загрузка): добавил файл загрузки данных о спутниках

Почему: требуется автоматизировать получение актуальных орбитальных данных из CelesTrak и сохранить их для последующей обработки.

Файлы:
- src/orbital_data_platform/collectors/celestrak.py: добавил загрузчик данных из CelesTrak
- tests/test_celestrak.py: добавил тесты проверки загрузчика
```

Заголовок отвечает на вопрос «Что сделано?», блок `Почему` — «Зачем это сделано?», список в конце — «Какие файлы затронуты?».

## 4. Типы коммитов

| Тип | Когда использовать | Пример |
|---|---|---|
| новое | Добавление новой возможности | `новое(загрузка): добавил загрузчик данных о спутниках` |
| исправление | Исправление ошибки в поведении | `исправление(sql): исправил расчёт суммы заказа` |
| документация | Изменение документации и комментариев | `документация(проект): описал формат входного файла` |
| стиль | Форматирование без изменения логики | `стиль(etl): привёл имена функций к PEP 8` |
| переработка | Изменение структуры без смены поведения | `переработка(загрузка): разделил функцию загрузки` |
| ускорение | Оптимизация времени или памяти | `ускорение(sql): оптимизировал запрос расчёта` |
| тесты | Добавление или изменение тестов | `тесты(загрузка): добавил тест на пустой файл` |
| сборка | Зависимости и сборка проекта | `сборка(зависимости): добавил библиотеку pyarrow` |
| автоматизация | Автоматические проверки и запуск | `автоматизация(проверки): добавил запуск тестов` |
| прочее | Служебные изменения, не подходящие под другие типы | `прочее(настройки): добавил правила коммитов` |
| откат | Отмена предыдущего коммита | `откат(загрузка): отменил изменение формата файла` |

## 5. Как выбрать тип

- Изменилось поведение для пользователя или данных — `новое` или `исправление`.
- Поведение осталось прежним, изменилась структура кода — `переработка`.
- Изменилось только форматирование — `стиль`.
- Изменилось только время выполнения или потребление памяти — `ускорение`.
- Изменилась только документация — `документация`.
- Изменились только тесты — `тесты`.
- Изменились зависимости или настройки сборки — `сборка`.
- Изменились автоматические проверки — `автоматизация`.
- Изменение не подходит под остальные типы — `прочее`.

## 6. Область коммита

Область указывается в круглых скобках после типа.

Допустимые варианты:
- короткое русское название: `загрузка`, `отчёты`, `настройки`, `зависимости`;
- название папки или модуля проекта: `sql`, `etl`, `api`.

Область должна отражать основную часть проекта, к которой относится изменение.

## 7. Несовместимые изменения

Если изменение нарушает обратную совместимость, необходимо:

1. Добавить `!` после области в заголовке.
2. Добавить в тело строку `ВАЖНО:` с описанием необходимых действий.

Пример:

```text
новое(загрузка)!: добавил поле времени получения в формат заказов

Почему: необходимо сохранять время получения данных отдельно от времени создания заказа.

ВАЖНО: перед запуском выполнить миграцию базы данных.

Файлы:
- src/load_orders.py: добавил чтение нового поля
- migrations/0003_add_received_at.py: добавил колонку времени получения
```

## 8. Проверка заголовка

Заголовок должен соответствовать шаблону:

```text
тип(область): описание
```

Допустимые типы:

```text
новое
исправление
документация
стиль
переработка
ускорение
тесты
сборка
автоматизация
прочее
откат
```

Дополнительные требования:
- область указывается в круглых скобках;
- после двоеточия ставится пробел;
- описание не должно быть пустым;
- ~~длина заголовка не превышает 72 символа;~~
- для несовместимых изменений используется `!` после области.

## 9. Проверка коммитов с помощью хуков

Хук `commit-msg` проверяет заголовок перед созданием коммита.

Проверка контролирует:
- допустимый тип;
- наличие области;
- формат заголовка;
- ~~длину не более 72 символов.~~

Хуки подключаются только к конкретному проекту.

### Расположение файлов

Исходники хуков:

```text
$HOME\.git-hooks\
├── commit-msg
└── check_commit_message.py
```

Подключённые хуки:

```text
.git\hooks\
├── commit-msg
└── check_commit_message.py
```

### Подключение хуков

check_commit_message.py
```python
import re
import sys

ALLOWED_TYPES = (
    "новое|исправление|документация|стиль|переработка|ускорение|"
    "тесты|сборка|автоматизация|прочее|откат"
)
HEADER_PATTERN = rf"^({ALLOWED_TYPES})\([\w-]+\)!?: .{{3,}}$"
#MAX_HEADER_LENGTH = 72

with open(sys.argv[1], encoding="utf-8") as message_file:
    header = message_file.readline().rstrip("\r\n")

if not re.match(HEADER_PATTERN, header):
    print("Неверный заголовок коммита.")
    print("Формат: тип(область): описание")
    print("Пример: исправление(sql): исправить расчёт суммы заказа")
    print("Типы: " + ", ".join(ALLOWED_TYPES.split("|")))
    sys.exit(1)

#if len(header) > MAX_HEADER_LENGTH:
#    print(f"Заголовок длиннее {MAX_HEADER_LENGTH} символов.")
#    sys.exit(1)
```


commit-msg
```powershell
#!/bin/sh
python "$(dirname "$0")/check_commit_message.py" "$1"
```

### Проверка

Неверный заголовок должен быть отклонён:

```powershell
git commit --allow-empty -m "что-то сделал"
```

Правильный заголовок должен пройти проверку:

```powershell
git commit --allow-empty -m "прочее(настройки): проверил работу хука"
```

Пробные коммиты удалять только в том случае, если они действительно созданы специально для проверки.

```powershell
git update-ref -d HEAD
```

**Внимание:** команда удаляет ссылку текущей ветки на коммит. Не использовать её для обычного удаления коммитов.

### Изменение хуков

Изменить правила можно в файле:

```text
.git\hooks\check_commit_message.py
```

Для добавления нового типа необходимо изменить `ALLOWED_TYPES`.

Файлы сохранять в UTF-8 без BOM. Для `commit-msg` использовать окончания строк LF.

### Временно отключить проверку

```powershell
Rename-Item ".git\hooks\commit-msg" "commit-msg.off"
```

Включить обратно:

```powershell
Rename-Item ".git\hooks\commit-msg.off" "commit-msg"
```

Пропустить проверку один раз:

```powershell
git commit --no-verify -F COMMIT_MSG.txt
```

Использовать пропуск только при обоснованной необходимости.

## 10. Просмотр истории коммитов

```powershell
# Полная история
git log

# Краткая история
git log --oneline

# Последний коммит
git log -1

# Название последнего коммита
git log -1 --format=%s

# Последние 5 коммитов
git log -5 --oneline

# История с графом веток
git log --oneline --graph --all

# Информация о последнем коммите
git show HEAD

# Изменения последнего коммита
git show --stat HEAD

# Состояние рабочей директории
git status
```

## 11. Удаление и отмена коммитов

### Удалить последний коммит, оставив изменения в индексе

```powershell
git reset --soft HEAD~1
```

### Удалить последний коммит, оставив изменения в файлах

```powershell
git reset --mixed HEAD~1
```

### Удалить последний коммит вместе с изменениями

```powershell
git reset --hard HEAD~1
```

### Удалить последние три коммита, оставив изменения

```powershell
git reset --soft HEAD~3
```

### Удалить последние три коммита вместе с изменениями

```powershell
git reset --hard HEAD~3
```

### Удалить конкретный коммит через интерактивное изменение истории

```powershell
git rebase -i HEAD~5
```

В открывшемся списке заменить `pick` на `drop` для коммитов, которые нужно удалить.

### Отменить последний коммит новым коммитом

```powershell
git revert HEAD
```

### Отменить конкретный коммит

```powershell
git revert <commit_hash>
```

Для уже опубликованных коммитов предпочтительно использовать `git revert`, чтобы не переписывать общую историю.

## 12. Восстановление коммитов

### Посмотреть историю перемещений HEAD

```powershell
git reflog
```

### Восстановить состояние на конкретном коммите

```powershell
git reset --hard <commit_hash>
```

Команда `reset --hard` удаляет незакоммиченные изменения. Перед её использованием необходимо проверить состояние рабочей директории.

## 13. Работа с удалённым репозиторием

```powershell
# Отправить изменения
git push

# Принудительно отправить изменения с проверкой
git push --force-with-lease

# Получить сведения об удалённом репозитории
git fetch

# Посмотреть удалённые ветки
git branch -r

# Добавить удалённый репозиторий GitHub
git remote add origin https://github.com/DrHy6yC/orbital_data.git

# Добавить удалённый репозиторий GitLab
git remote add gitlab https://gitlab.com/drhy6yc/orbital_data.git

# Создать общий удалённый репозиторий "all" с первым адресом (GitHub)
git remote add all https://github.com/DrHy6yC/orbital_data.git

# Добавить в "all" второй адрес (GitLab)
git remote set-url --add all https://gitlab.com/drhy6yc/orbital_data.git

# Отправить ветку main сразу на GitHub и GitLab
git push all main
```
