# Хранилища данных

Состояние на 2026-11-17. Документ описывает, где и в каком виде хранятся
данные проекта, как они копируются и в каком порядке восстанавливаются.
Пункты, которые ещё не реализованы или не проверены на практике,
отмечены явно.

## 1. Принцип

- Слои **Bronze** (исходные ответы источников) и **Silver** (нормализованный
  Parquet) хранятся в S3.
- Слой **Gold** (аналитические витрины) в S3 не хранится: он строится
  в ClickHouse через dbt и при потере пересобирается из Silver.
- Bronze не изменяется. Silver пересобирается из Bronze. Поэтому
  Bronze единственный слой, потеря которого необратима.
- Метаданные прогонов, снимков и копий ведутся в PostgreSQL.

## 2. Роли хранилищ

| Хранилище | Роль | Что хранит | Как запускается | Кто пишет |
|---|---|---|---|---|
| RustFS | Основное | Bronze, Silver | Docker, сервис `s3` в `docker-compose.yml` | Загрузчик (4.4), обработка (5.8) |
| MinIO | Локальный дубль | Bronze, Silver | Локальный процесс без Docker, `utils/run_minio.*` | Только скрипт дублирования (4.5) |
| Yandex Object Storage | Внешний бэкап | Bronze (gzip), дампы PostgreSQL | Облако, бесплатный уровень | Только скрипт бэкапа (4.6) |
| ClickHouse | Аналитика | Таблицы Silver, витрины Gold | Docker (6.1, не начато) | Загрузка Silver (6.4), dbt (6.7) |
| PostgreSQL | Метаданные | Прогоны, снимки, копии | Docker, сервис `postgres` | Загрузчик, скрипты копирования |

Почему MinIO не в Docker: публичные образы MinIO недоступны, поэтому он
собирается из исходников (инструкция: `MINIO_INSTALL_LOCAL.md`).
Проект MinIO заморожен, поэтому он используется только как дубль, а не как
основное хранилище.

Локальный каталог `data/` содержит снимки, сохранённые загрузчиком (3.4).
Это промежуточная копия на диске: из неё выгружается Bronze в RustFS (4.4).
Срок хранения файлов в `data/` определяется в 4.9.

## 3. Где лежит каждый слой

| Слой | RustFS | MinIO | Yandex | ClickHouse |
|---|---|---|---|---|
| Bronze | да, бакет `bronze` | да, дубль | да, `bronze/` в gzip, только окно хранения | нет |
| Silver | да, бакет `silver` | да, дубль | нет | таблицы, загруженные из Parquet |
| Gold | нет | нет | нет | да, витрины |
| Дампы PostgreSQL | нет | нет | да, `postgres/` | нет |

Silver в Yandex не копируется: он пересобирается из Bronze, а бесплатного
объёма облака (1 ГБ) на него не хватит.

## 4. Потоки данных

```text
CelesTrak / Space-Track
          |
          v
   Python (collectors)
          |
          v
   data/  (локальные снимки)
          |  4.4: выгрузка
          v
   RustFS: bronze ---- 4.5: копирование ----> MinIO: bronze
          |
          +------ 4.6: gzip, окна хранения --> Yandex: bronze/
          |
          v
   PyArrow -> Parquet
          |
          v
   RustFS: silver ---- 4.5: копирование ----> MinIO: silver
          |
          +--> DuckDB (локальные проверки)
          |
          +--> ClickHouse (загрузка Silver) --> dbt --> Gold в ClickHouse
```

Дамп PostgreSQL выгружается в Yandex в папку `postgres/` отдельно от Bronze.

## 5. Схема ключей

Bronze в RustFS и MinIO (бакет `bronze`, имя бакета в ключ не входит):

```text
<источник>/<набор>/<время UTC>.<расширение>
space_track/gp/2026-11-16T15-19-04Z.json
celestrak/gp_active/2026-11-16T15-19-04Z.csv
```

Совпадает с путём локального снимка `data/<источник>/<набор>/<время UTC>.<расширение>`.

Bronze в Yandex (бакет `BACKUP_S3_BUCKET`, окончание `.gz` добавляется
к исходному имени):

```text
bronze/<источник>/<набор>/<время UTC>.<расширение>.gz
```

Дампы PostgreSQL в Yandex:

```text
postgres/<база>_<время UTC>.sql.gz
```

Silver в RustFS и MinIO (бакет `silver`, имя бакета в ключ не входит).
Ключ повторяет Bronze и добавляет версию модели и дату снимка:

```text
<источник>/<набор>/schema=<версия>/dt=<дата UTC>/<время UTC>.parquet
space_track/gp/schema=v1/dt=2026-11-23/2026-11-23T07-33-20Z.parquet
celestrak/gp_active/schema=v1/dt=2026-11-23/2026-11-23T07-33-20Z.parquet
celestrak/gp_stations/schema=v1/dt=2026-11-23/2026-11-23T07-33-20Z.parquet
```

Правила ключа и партиционирования:

- `<версия>` — версия модели Silver (`v1`, `v2`, ...); состав полей `v1`
  определяется в 5.2. Версия меняется только при несовместимом изменении
  полей: переименование, удаление, смена типа. Новая необязательная
  колонка остаётся в текущей версии. Файлы разных версий лежат рядом,
  и одна модель их не читает.
- `dt=<дата UTC>` — дата снимка по UTC, а не по местному времени:
  снимок `2026-11-23T21-00-00Z` попадает в `dt=2026-11-23`.
- `<время UTC>` совпадает с именем снимка Bronze, поэтому пару объектов
  Bronze и Silver можно найти по имени.
- Один объект — один снимок одного набора. Дробление по размеру
  и склейка снимков в один файл в первой версии не применяются:
  `celestrak/gp_stations` даёт меньше 3 КБ на снимок, а склейка
  усложняет повторную запись и происхождение. Если файлов станет слишком
  много, компакция появится отдельной задачей.
- `dt=` — партиция: по ней можно читать только нужные даты, не перебирая
  всю историю набора.
- Silver окнами хранения не удаляется (раздел 8.1). Файлы старой версии
  удаляются только отдельным решением после перехода на новую.

Хранилища совпадают по ключам: объект, найденный в RustFS, должен
находиться в MinIO по тому же ключу.

## 6. Настройки

Все настройки в `.env` (образец: `.env.example`). Каждое S3-хранилище
описывается переменными `S3_<ИМЯ>_HOST`, `_PORT`, `_CONSOLE_PORT`,
`_ACCESS_KEY`, `_SECRET_KEY` (`RUSTFS`, `MINIO`). Параметры облака имеют
префикс `BACKUP_`: адрес и ключи Yandex
(`BACKUP_S3_ENDPOINT`, `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET`,
`BACKUP_S3_ACCESS_KEY`, `BACKUP_S3_SECRET_KEY`), имя локального источника
`BACKUP_SOURCE` (по умолчанию `RUSTFS`), лимит `BACKUP_MAX_MB`
и число дампов `BACKUP_KEEP_DUMPS`. Облако вынесено в отдельный префикс,
чтобы `utils/check_s3.py` не принимал его за локальное хранилище и не
создавал в нём бакеты.

### 7.2. Локальные хранилища

Окно хранения Bronze в RustFS и MinIO: 10 дней (значение в `.env`,
реализуется в 4.9). При загрузке `GP` раз в час, `ACTIVE` раз в два часа,
`SATCAT` и `DECAY` раз в день это около 18,7 ГБ на хранилище и около
37 ГБ на оба (расчёт по размерам из 7.1, без сжатия и дедупликации).
Дедупликация по sha256 (4.9) уменьшит объём, если содержимое набора
не изменилось.

### 7.3. Yandex Object Storage

Бесплатный уровень по
[правилам тарификации Object Storage](https://yandex.cloud/ru/docs/storage/pricing#rules)
(сверять с актуальной версией): 1 ГБ хранения, 10 000 операций
PUT, POST, PATCH, LIST и 100 000 операций GET, HEAD, OPTIONS в месяц.

Параметры проекта:

- `BACKUP_MAX_MB=800`: скрипт останавливает копирование, если размер бакета
  превысил бы лимит;
- целевой суммарный объём окон хранения не более 700 МБ;
- целевые окна хранения: `GP` 2 дня, `ACTIVE` 3 дня, `SATCAT` и `DECAY`
  14 дней, `STATIONS` 30 дней;
- удаляются только объекты `bronze/` по истечении окна своего набора
  и только после успешной загрузки новых;
- число операций записи при часовой загрузке `GP`: примерно 1 500 в месяц
  (оценка), лимит 10 000.

## 8. Резервное копирование и восстановление

Оригиналы слоёв лежат в RustFS, копии — в MinIO и Yandex. Команды
запускаются из корня проекта, их список — в разделе 9.

### 8.1. Что и куда копируется

| Что | Куда | Чем | Окно хранения |
|---|---|---|---|
| `bronze`, `silver` | MinIO, те же ключи | `utils/sync_storage.py` | Bronze 10 дней (7.2), Silver бессрочно |
| `bronze`, gzip | Yandex, каталог `bronze/` | `utils/backup_to_cloud.py` | `BACKUP_KEEP_<НАБОР>_DAYS` (7.3) |
| PostgreSQL, gzip | Yandex, каталог `postgres/` | `utils/backup_to_cloud.py` | последние `BACKUP_KEEP_DUMPS` дампов |

Правила:

- копирование между хранилищами ничего не удаляет; удаление есть только
  в Yandex и только по окнам хранения;
- последний снимок набора в Yandex не удаляется, даже если он старше
  окна хранения;
- объекты `_healthcheck/` не копируются;
- копии в RustFS, MinIO и Yandex отмечаются в `orbital.snapshot_copies`:
  `storage = 'rustfs'` пишет загрузчик, `storage = 'minio'` — дублирование,
  `storage = 'yandex'` — бэкап; у копии Yandex ключ облака (`bronze/...gz`)
  и размер сжатого объекта;
- перед сменой версии образа сначала выполняются оба копирования
  и дамп PostgreSQL.

### 8.2. Откуда восстанавливаться

Источники по убыванию удобства: MinIO (локально и быстро), Yandex
(нужен интернет, доступны только снимки в пределах окон хранения),
каталог `data/` (снимки, которые ещё не удалены).

Проверено 2026-11-17: пять последних снимков и дамп скачаны из облака,
распакованы gzip, `sha256` совпал с метаданными объектов и с оригиналами
в `data/`. Проверку выполняет `utils/check_backup_restore.py` (раздел 9).
Полное развёртывание дампа в пустую базу ещё не проверялось.

1. **Потерян RustFS, MinIO цел.** Скопировать бакеты из MinIO в RustFS
   командой из раздела 9 (`--from MINIO --to RUSTFS`), затем сверить
   листинги. Копирование ничего не удаляет в MinIO и создаёт
   отсутствующие бакеты в RustFS.
2. **Потеряны оба локальных хранилища.** Взять Bronze из Yandex
   скриптом `utils/restore_from_cloud.py`: он скачивает объект
   `bronze/<источник>/<набор>/<время>.<расширение>.gz`, распаковывает
   gzip, сверяет `sha256` с метаданными объекта и с записью
   `checksum_sha256` в `snapshots`, затем кладёт файл в RustFS
   без `bronze/` и без `.gz`:

   ```bash
   uv run --env-file .env python utils/restore_from_cloud.py --dry-run
   uv run --env-file .env python utils/restore_from_cloud.py
   uv run --env-file .env python utils/restore_from_cloud.py --dataset celestrak/gp_stations
   ```

   Дамп PostgreSQL разворачивается до запуска: без таблицы `snapshots`
   восстановленные копии не с чем связать. Какие снимки лежат в облаке,
   видно по строкам `storage = 'yandex'` в `snapshot_copies`: там облачный
   ключ и размер сжатого объекта. Скрипт берёт последний снимок
   каждого набора: более старые снимки возвращаются из MinIO или `data/`.
   История за пределами окон хранения потеряна, если её нет в `data/`.
3. **Потерян Silver.** Пересобрать из Bronze (этап 5), затем скопировать
   в MinIO по 4.5.
4. **Потерян ClickHouse (Gold).** Загрузить Silver (6.4) и выполнить
   `dbt run` (6.7).
5. **Потерян PostgreSQL.** Развернуть последний дамп из `postgres/`:
   скачать, распаковать gzip, сверить `sha256` с метаданными, затем
   восстановить в базу. Записи после времени дампа восстанавливаются
   по листингу хранилищ.

### 8.3. Переезд на другое устройство

База метаданных переносится вместе с объектами: `snapshots.storage_path`
и `snapshot_copies.object_key` ссылаются на ключи в хранилищах. Если
перенести базу без объектов или объекты без базы, сверка из раздела 9
покажет расхождения, а восстановление не сможет связать копии
со снимками.

| Что | Где лежит | Обязательность |
|---|---|---|
| PostgreSQL | каталог `postgres-data` | обязательно |
| RustFS | том Docker `orbital_data_s3-data` | обязательно |
| MinIO | каталог `storage/minio` | обязательно |
| Снимки | каталог `data/` | по желанию |

Имя тома включает имя проекта Compose, то есть имя каталога проекта.
При переезде каталог нужно назвать так же или отдельно перенести данные
тома в новый том.

Порядок:

1. Остановить загрузку и служебные скрипты, затем контейнеры:
   `docker compose stop`. Иначе во время копирования появятся новые
   объекты и строки в базе.
2. Выполнить `utils/backup_to_cloud.py`: в облако попадут дамп
   PostgreSQL и сжатые снимки Bronze.
3. Скопировать на новое устройство каталог `postgres-data`, том
   `orbital_data_s3-data`, каталог `storage/minio` и дамп из облака.
4. На новом устройстве выполнить `docker compose up -d`, развернуть
   дамп в базу и положить каталог `storage/minio` на место.
5. Проверить: `utils/check_snapshots.py` не должен показывать
   расхождений, `utils/check_s3.py --list` — бакеты и объекты,
   `utils/check_backup_restore.py` — копии в облаке.

Метаданные после переезда восстанавливаются из дампа или по листингу
хранилищ. Проверено 2026-11-23: пять снимков от 2026-11-17 остались
в бакете `bronze`, но пропали из `orbital.snapshots` — в базе был только
прогон от 2026-11-22. Снимки восстановлены из дампа
`postgres/orbital_data_2026-11-19T08-38-59Z.sql.gz`: размеры и `sha256`
совпали с объектами в обоих хранилищах. Скрипт
`sql/repair/2026_11_17_restore_metadata.sql` дописывает два прогона,
пять снимков и десять копий `rustfs` и `minio`, не меняя существующие
записи; снимки того же дня, которых в хранилище уже нет, в базу
не переносились. Копии `yandex` отметит ближайший запуск
`utils/backup_to_cloud.py`. Объекты `2026-11-17T12-25-52Z`, оставшиеся
только в облаке и отсутствующие в дампах, удалит окно хранения
`BACKUP_KEEP_*_DAYS`; метаданных у них нет.

## 9. Проверка

Все команды выполняются из корня проекта.

Работа S3-хранилищ, описанных в `.env` (создаёт бакеты, пишет, читает,
удаляет тестовые объекты):

```bash
uv run --env-file .env python utils/check_s3.py
```

Список бакетов и объектов без изменения данных:

```bash
uv run --env-file .env python utils/check_s3.py --list
```

Сверка объектов `bronze` в RustFS и MinIO с таблицей `orbital.snapshots`
(только чтение): печатает объекты без строки в `snapshots`, строки без
объекта и расхождения размеров, завершается кодом 1 при расхождениях:

```bash
uv run --env-file .env python utils/check_snapshots.py
```

Дублирование Bronze и Silver в MinIO (направление RustFS → MinIO):

```bash
uv run --env-file .env python utils/sync_storage.py --dry-run
uv run --env-file .env python utils/sync_storage.py
```

Восстановление RustFS из MinIO (направление MinIO → RustFS):

```bash
uv run --env-file .env python utils/sync_storage.py --from MINIO --to RUSTFS --dry-run
uv run --env-file .env python utils/sync_storage.py --from MINIO --to RUSTFS
```

Доступ к облаку, план и полный прогон резервного копирования:

```bash
uv run --env-file .env python utils/backup_to_cloud.py --check
uv run --env-file .env python utils/backup_to_cloud.py --dry-run
uv run --env-file .env python utils/backup_to_cloud.py
```

Проверка восстановления: скачивает последние снимки каждого набора
и последний дамп, распаковывает gzip, сверяет `sha256` с метаданными
объекта и с оригиналом в `data/`:

```bash
uv run --env-file .env python utils/check_backup_restore.py
```

Ключ `--key <ключ>` проверяет один объект, `--all` — весь бэкап.
В облаке выполняются только LIST, HEAD и GET.

Бэкап отмечает каждую копию Bronze в `orbital.snapshot_copies`
со `storage = 'yandex'`: ключ облака (`bronze/...gz`) и размер сжатого
объекта. Отмечаются и загруженные сейчас объекты, и уже лежавшие
в облаке; просроченные пропускаются, потому что этот же запуск их
удаляет. У объектов, лежавших в облаке до отметки, `copied_at` —
время отметки, а не загрузки.

Восстановление Bronze из облака в RustFS: скачивает последний снимок
каждого набора, распаковывает gzip, сверяет `sha256` с метаданными
объекта и с `snapshots`, загружает файл в бакет `bronze` и отмечает
копию `rustfs` в `snapshot_copies`:

```bash
uv run --env-file .env python utils/restore_from_cloud.py --dry-run
uv run --env-file .env python utils/restore_from_cloud.py
uv run --env-file .env python utils/restore_from_cloud.py --dataset space_track/gp
```

Ключ `--dataset <источник>/<набор>` ограничивает работу одним набором,
`--dry-run` читает только LIST и HEAD и ничего не скачивает.

## 10. Веб-интерфейсы хранилищ

Адреса указаны для значений по умолчанию из `.env.example`. Если порты
в `.env` изменены, подставьте свои.

| Хранилище | Адрес | Вход | Где меняется порт |
|---|---|---|---|
| RustFS | http://localhost:9001 | `S3_RUSTFS_ACCESS_KEY`, `S3_RUSTFS_SECRET_KEY` | `S3_RUSTFS_CONSOLE_PORT` |
| MinIO | http://127.0.0.1:9003 | `S3_MINIO_ACCESS_KEY`, `S3_MINIO_SECRET_KEY` | `S3_MINIO_CONSOLE_PORT` |
| Yandex Object Storage | https://console.yandex.cloud | аккаунт Yandex Cloud | не применимо |

Особенности:

- Консоли RustFS и MinIO слушают только `127.0.0.1`: они открываются
  на той машине, где запущено хранилище.
- RustFS работает в Docker (сервис `s3`), для консоли контейнер должен
  быть в состоянии `healthy`: `docker compose ps`.
- MinIO работает локальным процессом: пока окно с `utils/run_minio.*`
  закрыто, консоль недоступна.
- Прямая ссылка на бакет Yandex имеет вид
  `https://console.yandex.cloud/folders/<идентификатор каталога>/storage/buckets/<имя бакета>`.
  Идентификатор каталога виден в адресной строке консоли, имя бакета
  берётся из `BACKUP_S3_BUCKET`. Формат ссылки сверяйте с актуальной
  версией консоли.
- Без браузера содержимое локальных хранилищ показывает
  `uv run --env-file .env python utils/check_s3.py --list`, содержимое
  облачного бакета (первые 10 объектов) показывает
  `uv run --env-file .env python utils/yandex_probe.py`.
