### 1.4. Значимые факты

1. **Исчерпание 5-значных каталожных номеров.** По сообщению на сайте, 5-значные каталожные номера закончились 2026-07-11. Новые объекты получают номера от 100000, данных в формате TLE для них нет. Сайт рекомендует форматы без ограничения на длину номера (CSV, JSON, XML, KVN).
2. **Номер 101329** на сайте указан как текущий номер официального каталога USSF. Это наибольший присвоенный номер, а не количество объектов.
3. **Метка актуальности.** Страницы Current Data и SATCAT показывают "Current as of ..." с временем в UTC и номером дня в году. См. раздел 2.4.
4. **Дата последнего обновления у каждой страницы.** Внизу каждой страницы указана "Last updated". Для документации даты правок указаны явно, например: политика использования обновлена 2026-05-22, документация GP 2026-06-23, документация формата SATCAT 2026-09-23, запросы SupGP 2026-05-09. История правок отдельно не публикуется (см. раздел 6.6).

## 2. Current Data

**URL:** https://celestrak.org/NORAD/elements/
**Дата просмотра:** 2026-11-11

### 2.1. Назначение

Текущие GP-данные (General Perturbations) об орбитальных объектах. Названия GP и TLE обозначают одно и то же семейство данных: сайт называет страницу "A New Way to Obtain GP Data (aka TLEs)".

### 2.2. Источник наблюдений

На самой странице Current Data источник не указан. Он описан в документации "A New Way to Obtain GP Data":

- GP-данные производятся по наблюдениям Космической сети наблюдения США (US Space Surveillance Network, SSN) и рассчитываются как средние элементы Брауэра для модели SGP4.
- Данные CelesTrak получает через Space-Track от подразделения USSF. В тексте документации оно названо 18th Space Control Squadron (18 SPCS, текст 2020 года) и 18 SDS (в более новых разделах). Расшифровка 18 SDS на прочитанных страницах не приводится.
- В разделе о блокировках сказано: GP-данные CelesTrak "получает от Space Track", а 18 SDS GP-данные обновляются 2-3 раза в сутки.

Вывод: CelesTrak сам орбиты не измеряет и по этим данным является вторичным распространителем данных USSF. Это влияет на оценку доступности (раздел 5: при сбоях Space-Track данные CelesTrak тоже не обновляются; в документации описан такой сбой 2025-08-21...24).

### 2.3. Параметры запроса

Все запросы имеют вид `https://celestrak.org/NORAD/elements/gp.php?{QUERY}=VALUE[&FORMAT=VALUE]`. Имя параметра {QUERY} должно быть в верхнем регистре.

| Параметр | Назначение |
|---|---|
| CATNR | Каталожный номер (от 1 до 9 цифр), данные по одному объекту |
| INTDES | Международное обозначение запуска (гггг-ннн), все объекты запуска |
| GROUP | Группа объектов со страницы Current Data |
| NAME | Поиск по части названия |
| SPECIAL | Специальные наборы: gpz (GEO Protected Zone), gpz-plus, decaying (потенциальные сходы с орбиты) |
| FORMAT | Формат ответа: CSV (по умолчанию с 2026-05-09), JSON, JSON-PRETTY, XML, KVN, TLE, 2LE |

Имя параметра и значение `FORMAT` пишутся в верхнем регистре. Значения `GROUP` и `SPECIAL` на сайте указаны в нижнем регистре; в ответе на неверный запрос значение приводится к нижнему регистру (`GROUP=DEBRIS` дает `GROUP=debris not found`). Влияет ли регистр на успешный поиск, не проверено.

Примеры адресов (по документации и странице Current Data):

```text
# один объект по каталожному номеру (МКС)
https://celestrak.org/NORAD/elements/gp.php?CATNR=25544&FORMAT=JSON

# группа объектов
https://celestrak.org/NORAD/elements/gp.php?GROUP=stations&FORMAT=JSON

# специальный набор (GEO Protected Zone)
https://celestrak.org/NORAD/elements/gp.php?SPECIAL=gpz&FORMAT=CSV
```

Дополнительные запросы (из той же документации):

| Запрос | Назначение |
|---|---|
| gp-first.php | Первые доступные GP-данные для объекта или запуска. Полезно для первых данных по событию с обломками |
| gp.php (последние данные) | Используется самим CelesTrak для таблиц "Lost Objects" (/satcat/lost.php) и "Recently Decayed Objects" (/satcat/decayed-with-last.php) |
| table.php | Интерактивная таблица для группы (HTML), а не данные. Флаги: BSTAR, SHOW-OPS, OLDEST, DOCKED, MOVERS |

Ограничение на количество объектов в одном ответе в прочитанной документации не указано (параметра типа MAX для gp.php нет, он есть только у SATCAT). Данные по одному объекту получаются через CATNR. **Не проверено:** фактический размер ответа для крупных групп (ACTIVE, STARLINK) проверяется запросом в подэтапе 2.3.

### 2.4. Метки на странице

| Метка | Что означает |
|---|---|
| Current as of 2026 Nov 11 06:29:35 UTC (Day 315) | Время (UTC) и номер дня в году, на которое актуален набор. Что именно оно отражает (время приёма последнего GP от источника, время сборки страницы или другое) на странице не сказано. **Гипотеза:** время последнего обновления набора данных на CelesTrak. Проверить сопоставлением с `EPOCH` и временем загрузки |

### 2.5. Форматы

| Формат | Что это | Особенности |
|---|---|---|
| CSV | Ключи OMM в виде таблицы | **Формат по умолчанию для gp.php с 2026-05-09**. CelesTrak хранит данные у себя в CSV. По политике использования, CSV примерно на 10% меньше TLE и проще разбирается |
| JSON | Ключи OMM в JSON | Примерно в 3 раза больше CSV (по документации). Обязательные пустые и избыточные поля не включаются (CENTER_NAME, REF_FRAME, TIME_SYSTEM, MEAN_ELEMENT_THEORY) |
| JSON-PRETTY (JSON PP) | То же, что JSON, с форматированием | Для чтения человеком, больше по размеру |
| XML | OMM XML (CCSDS) со всеми обязательными элементами | Рекомендуется сайтом для критичных систем. Одно OMM около 1200 символов против 168 символов TLE |
| KVN | OMM в формате "ключ-значение" | Все обязательные элементы. Пустые значения могут быть пустыми |
| TLE / 3LE | Три строки: название (24 символа) и две строки элементов | Не поддерживает номера выше 99999 (по фактическому состоянию сайта: данных от 100000 нет) |
| 2LE | Две строки без названия | То же ограничение |

Для объектов без названия или международного обозначения (например, объекты 80000-серии, analyst) поля OBJECT_NAME и OBJECT_ID могут быть пустыми (blank в KVN, null в XML).

Следствие для платформы: поля JSON и CSV по составу совпадают, но JSON пропускает постоянные поля. Парсер должен допускать их отсутствие и не считать это ошибкой.

## 3. Supplemental GP Data (SupGP)

**URL:** https://celestrak.org/NORAD/elements/supplemental/
**Дата просмотра:** 2026-11-11

### 3.1. Отличие от GP (подтверждено на сайте)

| Признак | GP (Current Data) | SupGP |
|---|---|---|
| Основа | Наблюдения радарных и оптических средств SSN | Орбитальные данные, опубликованные владельцами и операторами спутников (эфемериды, альманахи, векторы состояния) |
| Кто рассчитывает | USSF (18 SDS), распространяется через Space-Track | CelesTrak сам рассчитывает GP по этим данным в STK и модели SGP4 |
| Цель | Каталог всех отслеживаемых объектов | Снижение задержки и повышение точности для объектов, чьи операторы публикуют данные |
| Поле Classification | "U" (unclassified) у данных, пришедших с Space-Track | "C" (источник CelesTrak) |
| Несколько записей на объект | Нет (одна актуальная) | Возможны: несколько источников (CPF) или несколько эпох |

Сайт указывает: для GPS неопределённость падает с нескольких километров до нескольких сотен метров (примерно на порядок). Для остальных группировок точность оценивается таблицами сравнения на сайте (SupGP vs. GP Comparisons). Это утверждение сайта, не проверенное нами.

**Что осталось гипотезой:** значение Classification у обычных GP может быть пустым в ответе API (в документации SupGP упоминается только "U"). Нужен реальный ответ (подэтап 2.3).

### 3.2. Запросы SupGP

Адрес: `https://celestrak.org/NORAD/elements/supplemental/sup-gp.php?{QUERY}=VALUE[&FORMAT=VALUE]`

| Параметр | Назначение |
|---|---|
| CATNR | Каталожный номер (1-9 цифр) |
| INTDES | Международное обозначение запуска |
| SOURCE | Источник данных (список ниже) |
| NAME | Часть названия |
| SPECIAL | GPZ или GPZ Plus |
| FILE | Имя стандартного набора на странице SupGP (starlink, oneweb, planet; также данные до запуска, например starlink-g4-22) |

Значения SOURCE: AST-E, CPF, CSS-E, EUMETSAT-E, GLONASS-RE, GPS-A, GPS-E, Intelsat-11P, Intelsat-E, Iridium-E, ISS-E, ISS-TLE, Kuiper-E, METEOSAT-SV, OneWeb-E, Orbcomm-TLE, Planet-E, SES-11P, SES-E, SpaceX-E, SpaceX-SV, Telesat-E, Transporter-SV, Bandwagon-SV.

Форматы те же, что у GP (TLE, 2LE, XML, KVN, JSON, JSON-PRETTY, CSV). Формат по умолчанию CSV с 2026-05-09.

### 3.3. Расписание

Расписание обновления у разных группировок разное; политика использования рекомендует ориентироваться на 2 часа. Точные расписания по источникам на прочитанных страницах не указаны.

### 3.4. Ответ на вопрос для модели данных

**Может ли у объекта быть одновременно GP и SupGP?** Да. Об этом прямо сказано: CelesTrak считает SupGP резервным источником на случай, когда GP отсутствуют или дают аномальные результаты, и предлагает использовать оба набора. Кроме того, у одного объекта может быть несколько SupGP-записей (разные источники или эпохи).

**Как различать при загрузке:**

1. Адрес запроса: `sup-gp.php` или `gp.php`.
2. Поле Classification: "C" у SupGP (подтверждено на сайте), "U" у GP (**гипотеза**, значение может быть пустым, см. 3.1).
3. Номер набора элементов (ELEMENT_SET_NO): у SupGP формируется по схеме источника (у GPS: неделя GPS и день недели), позволяет проследить исходные данные.
4. Название: у post-maneuver-записей Intelsat в конце названия стоит [PM]; у CPF после названия в скобках указан центр прогнозов.
5. Эпоха: SupGP считаются вперёд от текущей эпохи, а GP по прошлым наблюдениям (важно при выборе записи для SGP4).

Вывод для модели: ключом записи орбитальных элементов должна быть комбинация источника (GP / SupGP и SOURCE), каталожного номера и эпохи, а не только каталожный номер.

### 3.5. Польза для первой версии

Средняя. Данные полезны для точности, но усложняют модель (несколько записей на объект). **Предварительная рекомендация:** отложить, включить после GP и SATCAT. Окончательное решение фиксируется в 2.5.

## 4. SATCAT

**URL:** https://celestrak.org/satcat/
**Документация формата:** https://celestrak.org/satcat/satcat-format.php (обновлена 2026-09-23)
**Дата просмотра:** 2026-11-11

### 4.1. Поля каталога (CSV, подтверждено на сайте)

| Поле | Описание | Нужно платформе (предварительно) |
|---|---|---|
| OBJECT_NAME | Название. Сокращения: R/B(1), R/B(2) - ступени ракет, DEB - обломок, PLAT - платформа. В круглых скобках альтернативные названия, в квадратных типы объектов, "&" - соединённые объекты | Да |
| OBJECT_ID | Международное обозначение (ГГГГ-ННН + буквы, I и O не используются) | Да |
| NORAD_CAT_ID | Каталожный номер NORAD | Да (ключ связи с GP) |
| OBJECT_TYPE | PAY, R/B, DEB, UNK | Да |
| OPS_STATUS_CODE | Код эксплуатационного статуса (справочник /satcat/status.php) | Да |
| OWNER | Источник или владелец (справочник /satcat/sources.php) | Да |
| LAUNCH_DATE | Дата запуска (ISO 8601) | Да |
| LAUNCH_SITE | Место запуска (справочник /satcat/launchsites.php) | Да |
| DECAY_DATE | Дата схода с орбиты, если применимо | Да |
| PERIOD | Период, минуты; null при отсутствии данных | Хранить |
| INCLINATION | Наклонение, градусы; null | Хранить |
| APOGEE | Высота апогея, км; null | Хранить |
| PERIGEE | Высота перигея, км; null | Хранить |
| RCS | Радиолокационная заметность, м2; null | Хранить |
| DATA_STATUS_CODE | NCE (нет текущих элементов), NIE (нет начальных), NEA (элементов нет), иначе пусто | Да, важно для проверки качества |
| ORBIT_CENTER | Центральное тело (EA, MO, SU и т.д.) или NORAD_CAT_ID объекта, к которому пристыкован | Да |
| ORBIT_TYPE | ORB, LAN, IMP, DOC, R/T | Да |

Столбец "нужно платформе" предварительный. Для слоя Bronze хранится весь ответ целиком. Окончательное решение, какие поля попадут в Silver, принимается в 2.5. Поля PERIOD, INCLINATION, APOGEE, PERIGEE, RCS дублируют производные от GP и могут расходиться с ними по времени: это тема проверки согласованности в 2.4.

### 4.3. Старый формат (подтверждено)

Документация: старый текстовый формат (Legacy Text, фиксированные колонки) **не поддерживает объекты с каталожным номером выше 69999**. Также он не поддерживает Unicode, повышенную точность чисел и даты запуска и схода с орбиты со временем. "Старым форматом" называется именно файл `satcat.txt` с фиксированными колонками. CSV и JSON ограничений на номер не имеют.

Это совпадает с предупреждением на странице и с политикой использования. Проверка реальными данными (что в `satcat.txt` нет объектов с номерами 70000+) остаётся на 2.3.

## 6. Правила использования

**Политика:** https://celestrak.org/usage-policy.php (2026-05-15, обновлена 2026-05-22)
**Документация GP и FAQ о блокировках:** https://celestrak.org/NORAD/documentation/gp-data-formats.php (обновлена 2026-06-23, FAQ 2026-03-26)

### 6.1. Периодичность обновления

| Набор данных | Периодичность по сайту |
|---|---|
| GP | раз в 2 часа (сами данные USSF поступают 2-3 раза в сутки) |
| SupGP | разное расписание, рекомендуется 2 часа |
| SATCAT | вручную один-два раза в день |
| EOP | раз в сутки |
| Космическая погода | каждые 3 часа |
| SOCRATES Plus | каждые 10-11 часов (на момент публикации политики) |
| Данные GPS | как правило, раз в сутки |

### 6.2. Основные требования

1. Скачивать только нужные данные и только один раз за обновление.
2. Использовать запросы в соответствии с документацией.
3. Для наборов с каталогами актуальных файлов (`jsonDir.php`) проверять каталог перед загрузкой, не чаще раза в час.
4. Организациям с общим внешним IP-адресом (NAT) кешировать запросы на своей стороне.
5. Не скачивать лишнее: список STARLINK является подмножеством списка ACTIVE, поэтому скачивать оба не нужно (прямо сказано в документации). Группы предназначены для загрузки меньших наборов, а не всех подряд.

### 6.3. Поведение при ошибках (подтверждено на сайте)

Любой ответ, кроме HTTP 200, программа должна считать сигналом остановки и сообщить человеку.

| Код | Причина по сайту |
|---|---|
| 301 | Переадресация: другой домен (не `celestrak.org`, например `.com`) или устаревший запрос |
| 403 | Два вида. (1) Блокировка IP за чрезмерные запросы: сайт отправляет собственное сообщение с объяснением причины. (2) Повторная загрузка того же набора до очередного обновления (см. ниже) |
| 404 | Устаревший URL (например, удалённые статические файлы .txt) |
| 50x | Сервер перегружен, запросы нужно прекратить |

**Какие действия приводят к 403:**

1. **Повторный запрос до обновления данных (с 2026-03-26).** Применяется ко всем пользователям, начиная с групп ACTIVE и STARLINK. Первый запрос возвращает данные, второй возвращает HTTP 403 с текстом вида: "GP data has not updated since your last successful download of GROUP=active at <время> UTC. Data is updated once every 2 hours."
2. **Лимит ошибок:** при более чем 50 ошибках (301, 403, 404) за 2 часа IP-адрес отправляется в firewall (в более ранней редакции документации указывался порог 1000 ошибок в сутки, актуальным считать 50 за 2 часа).
3. **Расход трафика:** ранее вводились проверки пропускной способности (порог 100 МБ в сутки, затем 250 МБ в сутки), после чего сайт перешёл к принудительной политике "одна загрузка за обновление".
4. Продолжение избыточных запросов, даже успешных, может привести к блокировке IP-адреса.

**Снятие блокировки:** временные блокировки снимаются автоматически в течение 2 часов после прекращения запросов. Блокировка в firewall требует ручного разбора.

**Пустой и неожиданный ответ.** Код 200 ещё не означает, что пришли данные. Загрузчик должен отдельно обрабатывать:

1. Пустое тело ответа или тело без записей: успешной загрузкой не считать, файл в слой Bronze не записывать.
2. Тело не того типа: `text/plain` вместо JSON или CSV (см. 6.6), HTML-страница, обрезанный JSON.
3. Число записей заметно меньше обычного: порог задаётся на этапе 3.

**Недоступность источника.** На сайте описаны только коды 50x. Поведение при тайм-ауте, обрыве соединения и ошибке DNS на прочитанных страницах не описано, вопрос вынесен в раздел 9. Неудачная попытка не считается успешной загрузкой, поэтому повтор допустим, но число попыток и паузу между ними нужно ограничить на этапе 3.

### 6.4. Текущий статус принудительных ограничений

- Применяются для GP: группы ACTIVE и STARLINK (подтверждено).
- Для SupGP (STARLINK), SATCAT, SOCRATES, EOP и космической погоды политика от 2026-05-22 говорит "скоро" (soon). Более позднего подтверждения, что ограничения уже применяются, на прочитанных страницах нет. **Не проверено:** это определяется только практически, поэтому загрузчик должен вести себя так, будто ограничения действуют везде.

### 6.5. Что считать "одной загрузкой за обновление"

По сообщению сайта, учитывается успешная загрузка конкретной группы (в тексте ответа указано "GROUP=active"). Из прочитанных страниц не следует, что считается запросом: только `GROUP` или полный набор параметров (в том числе `FORMAT`), и действует ли правило между разными форматами одного набора. **Не проверено:** определяется экспериментом, но каждый такой эксперимент сам тратит лимит, поэтому рекомендация: считать "набором" комбинацию GROUP/FORMAT и не запрашивать один и тот же набор в двух форматах в одном окне обновления.

### 6.6. Проверенный запросом факт

Неверная группа возвращает **HTTP 200** с `Content-Type: text/plain` и телом вида `Invalid query: ... (GROUP=debris not found)`. Значит, проверки кода ответа недостаточно: загрузчик должен проверять тип содержимого и структуру тела (JSON или CSV с ожидаемыми полями). Источник: реальный запрос, на сайте это поведение не описано. Стоит перепроверить в подэтапе 2.3.

### 6.7. Право хранить и распространять данные

В прочитанных страницах (политика использования, документация GP) условий на хранение полученных данных или их повторную публикацию **не найдено**. Это не означает отсутствия условий: отдельная страница лицензии не открывалась. Для слоя Bronze и публикации проекта нужно проверить отдельно: условия на странице Documentation, а для данных Space-Track учесть их собственные условия, так как GP-данные USSF поступают через Space-Track.

### 6.8. История изменений политики

Единого журнала изменений на прочитанных страницах нет. Каждая страница показывает дату публикации и дату последней правки (для политики 2026-05-15 и 2026-05-22). Для отслеживания будущих правок предлагается при каждой проверке записывать значение "Updated" / "Last updated" страницы. Сайт также ведёт объявления в социальной сети (аккаунт автора указан на страницах).

### 6.9. Выводы для проекта (предварительные)

1. Повторные попытки загрузчика (этап 3.3) должны быть ограничены: при любом ответе, кроме 200 с ожидаемым телом, загрузчик останавливается и сообщает об ошибке.
2. Защита от повторной загрузки в окне обновления (связано с идемпотентностью, этап 3.7): перед запросом проверять, прошло ли 2 часа с последней успешной загрузки того же набора.
3. Использовать только актуальные URL на `https://celestrak.org`.
4. Проверять `Content-Type` и структуру тела, а не только код ответа (см. 6.6).
5. Хранить время успешной загрузки каждого набора: оно же служит ключом защиты от повторного запроса.

### 7.2. Обломки (DEBRIS)

Варианты получения полного набора обломков:

1. SATCAT: отбор по полю `OBJECT_TYPE` = DEB на стороне платформы из полного `satcat.csv`. Фильтра по типу объекта в параметрах `records.php` нет (есть только флаги PAYLOADS, ONORBIT, ACTIVE).
2. Запрос по `NAME` (например, часть названия "DEB"): поиск по части названия, результат зависит от соглашений об именах.
3. GP для найденных обломков: запрос по каждому `CATNR` отдельно недопустим по политике использования (слишком много запросов). Групповых запросов, покрывающих все обломки, на прочитанных страницах нет.

**Гипотеза (проверить в 2.3):** полный набор GP для всех обломков одним запросом получить нельзя. Задача решается комбинацией: SATCAT (список обломков с типом DEB) и существующих групп обломков, а также, возможно, `SPECIAL=DECAYING` для объектов, готовящихся к сходу. В SATCAT обломков на орбите: 10,383 отслеживаемых и 1,941 потерянных (см. 4.5).

## 8. Предварительные рекомендации по интеграции

Предварительные, будут уточнены в подэтапе 2.3.

1. Не строить архитектуру на формате TLE: он не поддерживает объекты с номерами от 100000.
2. Основной кандидат: JSON (OMM). Для экономии трафика и простоты парсинга CelesTrak сам хранит данные в CSV (формат по умолчанию). Окончательное решение после сравнения форматов на реальных ответах (подэтап 2.3). Учитывать, что JSON и CSV не содержат постоянных полей (CENTER_NAME, REF_FRAME, TIME_SYSTEM, MEAN_ELEMENT_THEORY).
3. Для SATCAT использовать CSV или JSON (API `records.php` или файл `satcat.csv`), а не старый формат `satcat.txt`.
4. Загрузчик: не чаще раза в 2 часа на набор, остановка при ответе, отличном от 200 или с неожиданным `Content-Type`, учёт времени успешной загрузки.
5. Хранить три временные характеристики раздельно: время получения платформой, метку обновления источника ("Current as of" / "Last updated"), `EPOCH`.
6. Модель орбитальных элементов должна допускать несколько записей на объект (разные источники GP / SupGP, разные эпохи).
7. Каждую запись помечать источником (GP или SupGP, значение SOURCE), так как у SupGP может быть несколько записей на объект.
