## 1. Общий обзор сайта

**URL:** https://celestrak.org
**Дата просмотра:** 2026-11-11

### 1.1. Назначение

CelesTrak публикует орбитальные данные об искусственных спутниках и других орбитальных объектах. Сайт ведёт Dr. T.S. Kelso. Данные доступны без регистрации и ключа API.

### 1.2. Структура меню

| Группа меню | Состав | Польза для платформы |
|---|---|---|
| Orbital Data | Current Data (GP), A New Way to Obtain GP Data, GPE Statistics, Special Data Request (GP), Supplemental Data (SupGP), How to Perform SupGP Queries, SupGP vs. GP Comparisons, SupGP Statistics, Special Data Request (SupGP), Documentation | Высокая: основной источник орбитальных элементов |
| Satellite Catalog | SATCAT, Search the SATCAT, SATCAT Documentation, SATCAT Boxscore, Launch Boxscore, Maps of Launch Sites | Высокая: каталожные сведения об объектах |
| SOCRATES | SOCRATES Plus, Search SOCRATES Plus, SOCRATES Plus Format Documentation | Низкая для первой версии: оценка сближений объектов, отдельная предметная область |
| Space Data | GPS Status, Almanacs, NANUs; Earth Orientation Parameters; Space Weather Data | Средняя: может пригодиться на этапе орбитальных вычислений (этап 8) |
| Library | Satellite Times Columns, публикации, программы, туториалы | Низкая: справочные материалы |

Boxscore-страницы (сводные таблицы по SATCAT и запускам) в рамках шага не открывались. Гипотеза: они могут служить независимой сводной статистикой для проверки качества данных (подэтап 2.4).

### 1.3. Значимые факты, выявленные при обзоре

1. **Исчерпание 5-значных каталожных номеров.** По сообщению на главной странице, 5-значные каталожные номера закончились 2026-07-11. Новые объекты получают номера от 100000, и данных в формате TLE для них не будет. Сайт рекомендует использовать другие форматы (CSV, JSON, XML, KVN), в которых ограничения на длину номера нет.
2. **Устаревший формат SATCAT.** Согласно сообщению на сайте, старый фиксированный формат SATCAT продолжит обновляться, но будет содержать только объекты с номерами ниже 70000. Это нужно перепроверить в подэтапе 2.3.
3. **Форматы GP на странице Current Data:** CSV, JSON, JSON PP (JSON с форматированием), OMM XML, OMM KVN, TLE/3LE, 2LE.
4. **Метка актуальности на странице Current Data.** Страница показывает время последнего обновления (на момент просмотра: 2026-11-11 06:29:35 UTC, день года 315). Это отдельная временная характеристика наряду с `EPOCH` (см. подэтап 2.4).
5. **Поиск групп по каталожному номеру.** Есть страница "Search GP Groups by Catalog Number" (`/NORAD/elements/master-gp-index.php`): по номеру объекта показывает все группы, в которые он входит. Относится к вопросу о пересечении групп (шаг 2.1.2).

### 5.1. Вопросы для ручной проверки страницы

1. Можно ли получить статистику в виде файла или через API, или это только графики и HTML-таблицы?
2. Как определяется "возраст" GP-данных: по `EPOCH` или по времени публикации?
3. Что означают категории "lost objects" и "restricted objects"? Влияют ли они на полноту каталога?
4. Как часто обновляется страница?
5. Доступна ли история среднего возраста с 2005 года для загрузки?

### 5.2. Предварительное решение

Если машиночитаемого доступа нет, статистику не использовать как источник. Свежесть данных оценивать по собственным данным платформы: разница между временем загрузки и `EPOCH`.

## 6. Правила использования

**URL:** https://celestrak.org/usage-policy.php
**Дата политики:** 2026-05-15, обновлена 2026-05-22
**Дата просмотра:** 2026-11-11

### 6.1. Периодичность обновления

| Набор данных | Периодичность по сайту |
|---|---|
| GP | раз в 2 часа |
| SupGP | разное расписание для разных группировок, рекомендуется использовать 2 часа |
| SATCAT | вручную один-два раза в день |
| EOP | раз в сутки |
| Космическая погода | каждые 3 часа |
| SOCRATES Plus | каждые 10-11 часов (на момент публикации политики) |
| Данные GPS | как правило, раз в сутки |

### 6.2. Основные требования

1. Скачивать только нужные данные и только один раз за обновление.
2. Использовать запросы в соответствии с документацией (GP, SupGP, SATCAT, SOCRATES Plus).
3. Для наборов с каталогами актуальных файлов (`jsonDir.php` для SATCAT, EOP и космической погоды, SOCRATES Plus, GPS) проверять каталог перед загрузкой. Обращаться к каталогам не чаще раза в час.
4. Ограничения принудительно применяются для крупных наборов: для GP это список Active, для GP и SupGP это список Starlink. Для SATCAT, SOCRATES, EOP и космической погоды применение ограничений ожидалось позже. По документации формата GP, политика "одна загрузка за обновление" применяется ко всем пользователям с 2026-03-26.
5. Многие пользователи ходят с одного IP-адреса (NAT). Организациям рекомендуется кешировать запросы на своей стороне.

### 6.3. Поведение при ошибках

Сайт сообщает, что при превышении лимитов или использовании устаревших URL отправляются HTTP-ошибки: 301, 403, 404, 50x. Программы (M2M) должны немедленно прекращать запросы при любом ответе, отличном от HTTP 200, и сообщать о результате человеку. Повторное игнорирование приводит к блокировке IP-адреса.

| Код | Значение по сайту |
|---|---|
| 301 | перенаправление: неверный домен (не `https://celestrak.org`) или устаревший формат запроса, перенаправление которого скоро прекратится |
| 403 | превышение лимитов (по списку кодов в политике, точная причина не расшифрована) |
| 404 | устаревший URL |
| 50x | сервер перегружен, запросы нужно немедленно остановить |

### 6.4. Выводы для проекта (предварительные)

1. Повторные попытки загрузчика (этап 3.3) не должны быть агрессивными. При ответе, отличном от 200, загрузчик останавливается, фиксирует ошибку и сообщает человеку.
2. Нужна защита от повторной загрузки в одном окне обновления (связано с идемпотентностью, этап 3.7).
3. Использовать только актуальные URL на домене `https://celestrak.org`.
4. Для SATCAT проверять `jsonDir.php`, чтобы не загружать неизменившиеся данные.
5. Точное поведение API (коды при превышении лимита, пустой ответ, неизвестная группа) проверяется экспериментально в подэтапе 2.3. До проверки считать эти пункты гипотезами.

## 8. Предварительные рекомендации по интеграции

Предварительные, будут уточнены после шагов 2.1.1-2, 2.1.1-3, 2.1.1-4 и подэтапа 2.3.

1. Не строить архитектуру на формате TLE: он не поддерживает объекты с номерами от 100000.
2. Основной кандидат для интеграции: JSON (OMM) и CSV. Окончательное решение принимается после сравнения форматов на реальных ответах (шаг 2.3.3).
3. Для SATCAT использовать JSON/CSV API, а не устаревший фиксированный формат.
4. Загрузчик должен соблюдать политику "одна загрузка за обновление" (GP: не чаще раза в 2 часа) и останавливаться при любом ответе, отличном от HTTP 200.
5. Хранить время получения данных отдельно от `EPOCH` и от метки обновления источника.
