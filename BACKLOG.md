### 4.0.3. Применение SQL-файлов без потери кириллицы

**Файл и место:** `README.md`, раздел «PostgreSQL и RustFS (Docker)»;
`sql/001_schema.sql`, `sql/002_seed.sql`.

**Что нужно сделать:** при применении справочника русские названия
наборов попали в `orbital.datasets` знаками вопроса. Причина —
передача файла в `psql` через конвейер PowerShell
(`Get-Content sql\002_seed.sql | docker compose exec ...`): консоль
заменяет символы вне своей кодовой страницы на `?`. Сам файл в
репозитории испорчен не был: он в UTF-8, портится именно передача.

Нужно:

- передавать файл в контейнер без перекодирования: скопировать его
  (`docker compose cp sql\002_seed.sql postgres:/tmp/002_seed.sql`)
  и выполнить `psql -f /tmp/002_seed.sql` внутри контейнера;
- добавить в начало `sql/001_schema.sql` и `sql/002_seed.sql` строку
  `SET client_encoding = 'UTF8';`;
- на устройстве с Windows таблица `orbital.datasets` сейчас
  отсутствует: `\dt orbital.*` показывает только `sources`, `runs`
  и `snapshots`. Применить схему заново и заполнить справочник;
- записать в `README.md` команды для Windows и для macOS: на macOS
  PowerShell не нужен, там работает обычное перенаправление ввода.

**Учесть:** повторное применение `sql/001_schema.sql` на уже
существующей схеме упадёт на `CREATE TABLE`; на рабочей базе
достаточно создать только отсутствующую таблицу либо применить
схему к пустой базе.

**Ожидаемый результат:** в `orbital.datasets` русские названия
читаются целиком, знаков `?` нет; команда из `README.md` на чистой
базе даёт тот же результат.

**Как проверить:**
- `docker compose exec -T postgres psql -U orbital -d orbital_data -c "SELECT code, title FROM orbital.datasets ORDER BY code;"` — пять строк с русскими названиями;
- `docker compose exec -T postgres psql -U orbital -d orbital_data -c "SELECT count(*) FROM orbital.datasets WHERE title LIKE '%?%';"` — ноль;
- `docker compose exec -T postgres psql -U orbital -d orbital_data -c "\dt orbital.*"` — четыре таблицы.

### 4.5. Дублирование Bronze и Silver в MinIO

**Файл и место:** `utils/sync_storage.py` (новый),
`tests/test_sync_storage.py` (новый).

**Что нужно сделать:**

хранилищ совпадает, второй запуск копирует ноль объектов.

**Как проверить:** тесты на поддельных клиентах для трёх случаев
(нет в MinIO, размеры совпадают, размеры различаются); живой прогон
дважды подряд.

### 4.6. Бэкап Bronze и PostgreSQL в Yandex с окнами хранения

**Файл и место:** `utils/backup_to_cloud.py`, `.env.example`,
`docs/storage.md`.

**Что нужно сделать:**

- измерить сжатие gzip на реальном снимке и записать коэффициент
  в `docs/storage.md`;
- выгружать Bronze в облако в gzip, исходник в RustFS не менять;
- окна хранения по наборам задать в `.env` и скорректировать после
  измерения сжатия так, чтобы суммарный объём не превышал 700 МБ
  при `BACKUP_MAX_MB=800`: ориентир — `GP` 2 дня, `ACTIVE` 3 дня,
  `SATCAT` и `DECAY` 14 дней, `STATIONS` 30 дней;
- учесть оценку из `docs/storage.md`: без сжатия эти окна дают около
  4,6 ГиБ, поэтому для 700 МБ нужно сжатие не менее чем в 6,8 раза;
  если измерение покажет меньше, сократить окно `GP` или выгружать
  в облако не каждый снимок `GP`;
- удалять в облаке только объекты `bronze/`, только по истечении окна
  своего набора и только после успешной загрузки новых;
- сохранить лимит `BACKUP_MAX_MB` и `BACKUP_KEEP_DUMPS` для дампов
  PostgreSQL;
- ключ `--dry-run` показывает план копирования и удаления.

**Ожидаемый результат:** бэкап укладывается в лимит, в облаке лежит
история за окна хранения, дампов PostgreSQL не больше заданного числа.

**Как проверить:** `--dry-run` до и после прогона; восстановление
одного объекта из `.gz` с совпадением sha256 с локальным оригиналом;
повторный запуск не копирует существующее.

### 4.7. Метаданные прогонов, снимков и копий в PostgreSQL

**Файл и место:** `sql/003_meta.sql` (новый),
`src/orbital_data/source_snapshots/registry.py` (новый),
`src/orbital_data/collectors/download.py`, `tests/test_registry.py`
(новый).

**Что нужно сделать:**

- новая таблица `orbital.snapshot_copies`: снимок, хранилище
  (`rustfs`, `minio`, `yandex`), ключ, размер, etag, статус, время;
- заполнять `runs` при старте и завершении прогона, статус `success`,
  `partial`, `failed`;
- заполнять `snapshots` после сохранения: sha256, размер, путь;
- писать копии в `snapshot_copies` после выгрузки в RustFS,
  синхронизации в MinIO и бэкапа в Yandex;
- подключение через psycopg, настройки из `POSTGRES_*`; зависимость
  устанавливает владелец проекта командой `uv add psycopg`;
- при недоступности базы снимки всё равно сохраняются, ошибка попадает
  в отчёт.

**Ожидаемый результат:** по каждому снимку видно, в каких хранилищах
он лежит и с каким статусом.

**Как проверить:** после прогона запросы к `orbital.runs`,
`orbital.snapshots` и `orbital.snapshot_copies` показывают один прогон,
пять снимков и копии по хранилищам; тест на частичный прогон даёт
статус `partial`.
