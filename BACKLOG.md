# Этап 2. Исследование источников данных

**Цель этапа:** определить доступные источники орбитальных данных,
изучить способы получения информации, оценить качество и ограничения
данных, а также сформировать основу для последующей реализации механизма
сбора и хранения данных в Orbital Data Platform.

На этом этапе полноценный механизм загрузки пока не разрабатывается.
Сначала исследуются источники, проверяются реальные ответы API и
определяется, какие данные целесообразно использовать в проекте.

## 2. Подробный план работ

### 2.1. Исследование CelesTrak

**Цель:** разобраться, какие данные предоставляет CelesTrak, как они
организованы и каким способом их можно получать.

**Ожидаемый результат:** карта возможностей источника.

#### Шаг 1. Изучение возможностей CelesTrak

Изучить официальный сайт CelesTrak и его основные разделы:

-   **Current Data** --- текущие наборы орбитальных данных.
-   **Supplemental GP Data** --- дополнительные орбитальные данные.
-   **SATCAT** --- каталог космических объектов.
-   **GPE Statistics** --- статистика и информация об актуальности
    орбитальных данных.

Для каждого раздела необходимо определить его назначение, состав данных
и потенциальную пользу для платформы.

#### Шаг 2. Исследование групп космических объектов

Изучить доступные группы и определить, какие объекты они содержат.

Для первоначального исследования предлагаются следующие группы:

  Группа        Назначение
  ------------- -----------------------------
  ACTIVE        Активные спутники
  STATIONS      Орбитальные станции
  STARLINK      Спутники Starlink
  ONEWEB        Спутники OneWeb
  GPS-OPS       Работающие спутники GPS
  GLONASS-OPS   Работающие спутники ГЛОНАСС
  GALILEO       Спутники Galileo
  WEATHER       Метеорологические спутники
  CUBESAT       Малые спутники CubeSat
  DEBRIS        Космический мусор и обломки

Для каждой группы необходимо выяснить:

1.  Какие объекты входят в группу.
2.  Сколько объектов содержит группа.
3.  Какие сведения доступны для каждого объекта.
4.  Как часто обновляются сведения.
5.  Пересекаются ли группы между собой.
6.  Можно ли получить информацию по отдельному объекту.

**Важно:** группы `ACTIVE` и другие тематические группы могут содержать
пересекающиеся объекты. Это необходимо учитывать при последующем
объединении данных.

#### Шаг 3. Исследование API

Изучить основной интерфейс получения GP-данных:

``` text
https://celestrak.org/NORAD/elements/gp.php
```

Исследовать доступные параметры запросов:

  Параметр   Назначение
  ---------- --------------------------------------------------------
  CATNR      Получение данных по каталожному номеру
  INTDES     Получение данных по международному обозначению запуска
  GROUP      Получение данных по группе объектов
  NAME       Поиск объектов по названию
  SPECIAL    Получение специальных наборов данных
  FORMAT     Выбор формата ответа

Примеры запросов:

``` text
# Получение данных по ISS
https://celestrak.org/NORAD/elements/gp.php?CATNR=25544&FORMAT=JSON

# Получение данных по группе Starlink
https://celestrak.org/NORAD/elements/gp.php?GROUP=STARLINK&FORMAT=JSON

# Получение данных по орбитальным станциям
https://celestrak.org/NORAD/elements/gp.php?GROUP=STATIONS&FORMAT=JSON

# Получение данных по спутникам GPS
https://celestrak.org/NORAD/elements/gp.php?GROUP=GPS-OPS&FORMAT=JSON
```

Отдельно изучить SATCAT API:

``` text
https://celestrak.org/satcat/records.php
```

Он позволяет получать каталог объектов, включая названия, международные
обозначения и другие каталожные сведения.

#### Шаг 4. Исследование форматов данных

Изучить доступные форматы представления GP-данных:

  -----------------------------------------------------------------------
  Формат                              Назначение
  ----------------------------------- -----------------------------------
  JSON                                Структурированные данные для
                                      программной обработки

  CSV                                 Табличное представление данных

  XML                                 Формат OMM в XML

  KVN                                 Формат OMM Key-Value Notation

  TLE / 3LE                           Двухстрочное представление
                                      орбитальных элементов с названием
                                      объекта

  2LE                                 Двухстрочное представление без
                                      отдельной строки названия
  -----------------------------------------------------------------------

Для Orbital Data Platform в первую очередь исследовать JSON и CSV.
Отдельное внимание уделить OMM --- формату обмена орбитальными данными,
поддерживающему более современные идентификаторы объектов.

**Технический момент:** TLE имеет ограничения на длину каталожного
номера и не подходит в качестве единственного формата для всех новых
объектов. Поэтому нельзя строить архитектуру платформы исключительно на
TLE. Основным кандидатом для интеграции следует рассматривать JSON с
данными OMM. Это предположение необходимо подтвердить проверкой
актуальной документации и реальных ответов API.

#### Шаг 5. Изучение правил использования API

Проверить и задокументировать:

-   периодичность обновления GP-данных;
-   ограничения на частоту запросов;
-   поведение API при повторном скачивании неизменившихся данных;
-   HTTP-коды ошибок;
-   возможность получения пустого ответа;
-   поведение при недоступности источника.

Следует учитывать рекомендации CelesTrak по частоте запросов. Необходимо
избегать избыточного скачивания одинаковых наборов и получать только те
данные, которые действительно используются платформой.

**Результат подэтапа 2.1:**

Документ `celestrak_research.md`, содержащий:

-   описание возможностей источника;
-   перечень групп объектов;
-   описание API и параметров запросов;
-   описание доступных форматов;
-   ограничения и правила использования;
-   предварительные рекомендации по интеграции.

### 2.2. Анализ структуры данных

**Цель:** определить, какую информацию фактически можно получить от
источника и как она представлена.

**Ожидаемый результат:** описание структуры данных.

#### Шаг 1. Изучение структуры GP-данных

Получить несколько объектов в JSON и изучить следующие поля:

  Поле                Назначение
  ------------------- ------------------------------------------
  OBJECT_NAME         Название объекта
  OBJECT_ID           Международное обозначение
  NORAD_CAT_ID        Каталожный номер
  EPOCH               Время актуальности орбитальных элементов
  MEAN_MOTION         Среднее движение
  ECCENTRICITY        Эксцентриситет
  INCLINATION         Наклонение орбиты
  RA_OF_ASC_NODE      Долгота восходящего узла
  ARG_OF_PERICENTER   Аргумент перицентра
  MEAN_ANOMALY        Средняя аномалия
  BSTAR               Коэффициент баллистического торможения

Для каждого поля определить:

-   фактический тип значения;
-   единицы измерения;
-   обязательность;
-   допустимость отсутствующего значения;
-   ограничения и особенности интерпретации.

#### Шаг 2. Изучение SATCAT

Исследовать каталог отдельно от GP-данных.

Рассмотреть следующие характеристики:

-   каталожный номер;
-   название объекта;
-   международное обозначение запуска;
-   тип объекта;
-   страна регистрации;
-   дата запуска;
-   дата схода с орбиты;
-   статус объекта;
-   дополнительные каталожные характеристики.

#### Шаг 3. Определение связей между наборами

Основной идентификатор для сопоставления объектов --- `NORAD_CAT_ID` в
GP-данных и соответствующий каталожный номер в SATCAT.

Проверить:

1.  Всегда ли присутствует идентификатор.
2.  Может ли объект присутствовать в SATCAT, но отсутствовать в GP.
3.  Может ли объект входить в несколько групп.
4.  Какие данные можно объединить по одному каталожному номеру.
5.  Как обрабатывать несовпадения и отсутствующие сведения.

**Результат подэтапа 2.2:**

Документ `celestrak_data_structure.md` с описанием полей, типов, единиц
измерения и связей между наборами данных.

### 2.3. Практическое исследование API

**Цель:** самостоятельно выполнить запросы к CelesTrak и убедиться, что
полученные данные соответствуют документации.

**Ожидаемый результат:** проверенные API-запросы и примеры ответов.

#### Шаг 1. Подготовка исследовательского окружения

Создать отдельную директорию для исследования:

``` text
research/
└── celestrak/
    ├── requests/
    ├── responses/
    ├── scripts/
    └── README.md
```

#### Шаг 2. Проверка запросов

Последовательно проверить:

1.  Получение одного объекта по `CATNR`.
2.  Получение группы по `GROUP`.
3.  Получение данных по `NAME`.
4.  Получение данных по `INTDES`.
5.  Получение SATCAT по каталожному номеру.
6.  Получение SATCAT для группы объектов.

Для каждого запроса сохранить параметры, HTTP-статус, заголовки ответа
(если они важны для анализа) и пример полученных данных.

#### Шаг 3. Проверка форматов

Для нескольких одинаковых объектов получить ответы в JSON, CSV и XML.

Сравнить:

-   состав полей;
-   структуру;
-   типы значений;
-   наличие пустых значений;
-   удобство обработки средствами Python;
-   возможность сохранить исходные данные без потери информации.

#### Шаг 4. Проверка ошибок и граничных ситуаций

Проверить следующие ситуации:

-   несуществующий каталожный номер;
-   некорректный параметр;
-   неизвестная группа;
-   пустой ответ;
-   ошибка HTTP;
-   некорректный формат ответа;
-   временная недоступность API.

Зафиксировать фактическое поведение API, не предполагая заранее
конкретный HTTP-код или структуру ошибки.

#### Шаг 5. Фиксация результатов

Сохранить примеры ответов и задокументировать результаты каждого
запроса. Скрипты должны позволять повторить исследование без ручного
формирования каждого запроса.

**Результат подэтапа 2.3:**

Набор воспроизводимых примеров работы с API, сохранённые ответы и
описание выявленного поведения API.

### 2.4. Оценка качества и актуальности данных

**Цель:** определить, насколько полученные сведения подходят для
использования в платформе.

**Ожидаемый результат:** критерии качества данных и результаты проверки.

Проверить следующие характеристики:

  Характеристика    Что проверяем
  ----------------- --------------------------------------------------
  Актуальность      Насколько давно обновлялись орбитальные элементы
  Полнота           Все ли необходимые поля присутствуют
  Достоверность     Корректность значений и их соответствие формату
  Идентификация     Возможность однозначно определить объект
  Согласованность   Совпадают ли идентификаторы в GP и SATCAT
  Доступность       Стабильность ответов API
  Обновляемость     Как часто появляются новые версии данных

Особое внимание уделить полю `EPOCH`. Это временная метка, определяющая
эпоху орбитальных элементов, и она важна для оценки актуальности орбиты.

Необходимо различать три временные характеристики:

-   время получения данных платформой;
-   время последнего обновления данных в источнике, если оно доступно;
-   эпоху орбитальных элементов (`EPOCH`).

Это разные временные характеристики, которые впоследствии должны
корректно учитываться платформой.

**Результат подэтапа 2.4:**

Документ `celestrak_data_quality.md` с критериями проверки качества и
результатами оценки полученных данных.

### 2.5. Выбор наборов данных для первой версии платформы

**Цель:** определить минимальный необходимый состав данных для запуска
первой версии Orbital Data Platform.

**Ожидаемый результат:** утверждённый перечень наборов данных.

На основании предыдущих исследований сформировать перечень источников и
разделить данные на три категории.

**1. Основные данные**

-   GP / OMM --- орбитальные элементы.
-   SATCAT --- каталог космических объектов.

**2. Дополнительные данные**

-   Supplemental GP --- дополнительные орбитальные решения.
-   Специальные группы объектов.
-   Данные о запусках и сходах с орбиты, если они доступны в необходимом
    объёме.

**3. Исследовательские данные**

-   статистика обновлений;
-   информация об устаревших объектах;
-   данные о потенциальном сходе объектов с орбиты.

Для каждого набора зафиксировать:

-   назначение;
-   источник;
-   способ получения;
-   формат;
-   необходимость использования;
-   приоритет интеграции;
-   ограничения и зависимости.

**Предварительная рекомендация:** для первой версии достаточно начать с
GP (OMM JSON) и SATCAT. Остальные наборы подключать по мере появления
конкретных требований к функциональности.

**Результат подэтапа 2.5:**

Перечень наборов данных первой версии с обоснованием выбора и
приоритетами интеграции.

### 2.6. Проектирование процесса сбора данных

**Цель:** определить, как платформа будет получать данные от внешнего
источника и передавать их на последующую обработку.

**Ожидаемый результат:** схема процесса сбора данных и описание его
правил.

На этом подэтапе загрузчик ещё не реализуется. Проектируется его
поведение и определяются требования к будущей реализации.

Предлагаемая последовательность:

``` text
CelesTrak API
     |
     v
Получение данных
(HTTP-запросы, параметры, форматы)
     |
     v
Проверка ответа
(HTTP-статус, структура, обязательные поля)
     |
     v
Передача на обработку
(подготовка данных к нормализации)
     |
     v
Хранение данных
(последующий этап разработки)
```

Исследовать и задокументировать:

1.  Частоту получения данных.
2.  Условия повторного запроса.
3.  Обработку ошибок API.
4.  Повторные попытки при временной недоступности.
5.  Проверку целостности полученного ответа.
6.  Предотвращение повторной обработки неизменившихся данных.
7.  Фиксацию времени получения и версии данных.

Важно заранее определить, что орбитальные элементы являются изменяемыми
данными: у одного объекта со временем появляется несколько версий
орбиты.

Поэтому повторное получение орбитальных элементов нельзя автоматически
рассматривать как создание нового космического объекта.

**Результат подэтапа 2.6:**

Документ `celestrak_data_collection.md` с описанием будущего процесса
сбора данных и его основных правил.

## 6. Порядок совместной работы

Подэтапы выполняются последовательно. Переходить к следующему подэтапу
следует после получения и фиксации результата предыдущего.

Начать необходимо с **2.1 --- Исследование CelesTrak**:

1.  Изучить официальный сайт и его основные разделы.
2.  Разобрать назначение групп и доступных наборов данных.
3.  Изучить API и его параметры.
4.  Проверить доступные форматы.
5.  Зафиксировать ограничения и предварительные выводы.

После этого перейти к практической проверке API и последующим подэтапам.

Главный принцип этапа: зафиксировать не только описание возможностей
источника, но и подтверждённые результаты практических проверок. Это
позволит обосновать решения по интеграции CelesTrak в Orbital Data
Platform.
