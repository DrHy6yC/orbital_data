# Рабочие заметки

# Хранилища, DuckDB и ClickHouse в Orbital Data Platform

## 1. Цель

В проекте три роли S3-хранилищ и две аналитические СУБД.

Хранилища: RustFS — основное, MinIO — локальный дубль, Yandex Object
Storage — внешний бэкап. Подробности: `docs/storage.md`.

Аналитика: DuckDB применяется для локального исследования и проверки
данных, ClickHouse — для серверной аналитики, хранения витрин Gold
и обслуживания запросов API.

## 2. Назначение компонентов

### 2.1. Хранилища

**RustFS** — основное S3-хранилище. В него пишут загрузчик (Bronze)
и обработка (Silver). Из него читают DuckDB и ClickHouse.

**MinIO** — локальный дубль Bronze и Silver. Запускается без Docker,
получает данные только от скрипта дублирования. В нём ничего не
удаляется при копировании.

**Yandex Object Storage** — внешний бэкап в пределах бесплатного уровня.
Хранит Bronze в gzip за окна хранения и дампы PostgreSQL. Silver туда
не копируется, он пересобирается из Bronze.

Gold в S3 не хранится: витрины живут в ClickHouse.

### 2.2. DuckDB

**Назначение:** локальная аналитическая обработка данных.

Основные задачи:

- Исследование новых наборов данных.
- Анализ структуры и содержимого Parquet.
- Выполнение SQL-запросов непосредственно к Parquet в S3 и на диске.
- Проверка результатов нормализации.
- Разработка и отладка аналитических запросов.
- Локальная проверка гипотез без загрузки данных в ClickHouse.

DuckDB не используется в качестве основного хранилища аналитических
данных и не участвует в проекте dbt.

### 2.3. ClickHouse

**Назначение:** основная серверная аналитическая СУБД.

Основные задачи:

- Хранение таблиц Silver, загруженных из Parquet.
- Хранение витрин Gold.
- Обработка больших объёмов данных.
- Анализ истории орбитальных параметров.
- Выполнение агрегирующих и аналитических запросов.
- Обслуживание аналитических запросов через FastAPI.

ClickHouse является единственным целевым движком dbt.

## 3. Архитектура взаимодействия

```text
CelesTrak / Space-Track
          |
          v
   Python (collectors)
          |
          v
   data/  (локальные снимки)
          |
          v
   RustFS: bronze ---- копирование ----> MinIO: bronze
          |
          +---- gzip, окна хранения ----> Yandex (бэкап)
          |
          v
   PyArrow / Parquet
          |
          v
   RustFS: silver ---- копирование ----> MinIO: silver
          |
          +-------------------+
          |                   |
          v                   v
       DuckDB             ClickHouse
   (локальные проверки)   (загрузка Silver)
                              |
                              v
                       dbt Core (dbt-clickhouse)
                              |
                              v
                       ClickHouse: Gold
                              |
                              v
                           FastAPI
```

Метаданные прогонов, снимков и копий ведутся в PostgreSQL параллельно
с этим потоком.

### 3.1. Поток данных

1. Python получает исходные данные из CelesTrak и Space-Track и сохраняет
   снимки в `data/`.
2. Снимки выгружаются в бакет `bronze` RustFS без изменений.
3. Скрипт дублирования копирует Bronze и Silver из RustFS в MinIO.
4. Скрипт бэкапа выгружает Bronze (gzip) и дампы PostgreSQL в Yandex.
5. PyArrow выполняет нормализацию и формирует Parquet-файлы Silver
   в RustFS.
6. DuckDB используется для локальной проверки Silver.
7. ClickHouse получает наборы Silver для аналитической обработки.
8. dbt выполняет преобразования и формирует витрины Gold в ClickHouse.
9. FastAPI предоставляет доступ к аналитическим данным.

## 4. Распределение ответственности

| Компонент | Ответственность |
|---|---|
| PostgreSQL | Метаданные, источники, история прогонов и копий |
| RustFS | Основное хранение Bronze и Silver |
| MinIO | Локальный дубль Bronze и Silver |
| Yandex Object Storage | Внешний бэкап Bronze и дампов PostgreSQL |
| PyArrow | Нормализация и работа с Parquet |
| DuckDB | Локальная аналитика и исследование данных |
| ClickHouse | Серверная аналитика, таблицы Silver, витрины Gold |
| dbt Core | SQL-трансформации и построение моделей в ClickHouse |
| Airflow | Оркестрация процессов |
| FastAPI | Предоставление данных через REST API |

## 5. Использование dbt Core

В проекте один dbt-проект с адаптером `dbt-clickhouse`. Все модели
staging, intermediate и витрины Gold строятся в ClickHouse.

DuckDB работает независимо от dbt: для локальных проверок используются
запросы из Python и вспомогательные скрипты, а не отдельный проект dbt.
Это исключает две версии одних и тех же моделей с разным синтаксисом
и функциями.

## 6. Принципы использования

1. Исходные данные Bronze сохраняются без изменений.
2. Silver хранится в Parquet в S3 (RustFS, дубль в MinIO).
3. Gold хранится только в ClickHouse, в S3 его нет.
4. DuckDB не заменяет постоянное хранилище Parquet.
5. ClickHouse используется как основная серверная аналитическая СУБД.
6. PostgreSQL сохраняет ответственность за операционные данные и метаданные.
7. DuckDB и ClickHouse не должны независимо реализовывать одинаковые
   производственные процессы без необходимости.
8. Перенос данных в ClickHouse не приводит к потере исходных файлов в S3.
9. Копирование между хранилищами ничего не удаляет, удаление выполняет
   только политика хранения (последний снимок набора не удаляется).

## 7. Развёртывание

- PostgreSQL, RustFS и ClickHouse работают в Docker.
- MinIO работает локальным процессом без Docker: публичные образы MinIO
  недоступны, инструкция сборки в `MINIO_INSTALL_LOCAL.md`.
- DuckDB используется из Python без отдельного серверного контейнера.
- Yandex Object Storage внешний сервис, доступ по статическому ключу
  из `.env`.

Для локальной разработки допускается одновременная работа DuckDB
и ClickHouse.

## 8. Преимущества выбранной схемы

- Исходные данные хранятся в нескольких местах: основное и локальное
  хранилища плюс внешний бэкап.
- Работа с Parquet без обязательной загрузки данных в ClickHouse.
- Серверная OLAP-СУБД для аналитических запросов и витрин.
- Разделение исследовательской и производственной аналитики.
- Практическое изучение двух разных подходов к аналитическим вычислениям.
- Единый dbt-проект без дублирования моделей.

## 9. Риски и что проверить

- Совместимость ClickHouse с RustFS и MinIO при чтении и записи через
  `s3()`, включая многочастную загрузку: проверяется в 6.1.
- Коэффициент сжатия gzip для снимков и достаточность бесплатного
  объёма Yandex при выбранных окнах хранения: измеряется в 4.6.
- MinIO заморожен как проект: он остаётся дублем, не основным хранилищем.

## 10. Итоговая архитектурная концепция

RustFS и Parquet остаются основой Lakehouse-хранилища, MinIO даёт
локальную копию, Yandex внешний бэкап. PostgreSQL отвечает за метаданные.

**DuckDB** — инструмент локальной аналитики, исследования и проверки данных.

**ClickHouse** — основная серверная аналитическая СУБД, используемая
для построения и обслуживания витрин Gold.

dbt и Airflow обеспечивают преобразование и автоматизацию процессов.
