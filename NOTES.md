# Рабочие заметки
# Использование DuckDB и ClickHouse в Orbital Data Platform

## 1. Цель

В проекте используются две аналитические СУБД: DuckDB и ClickHouse.

Каждая СУБД решает собственный круг задач. DuckDB применяется для локальной аналитики и исследования данных, ClickHouse — для серверной аналитики и обслуживания запросов.

Совместное использование позволяет работать с Parquet напрямую и одновременно иметь отдельную аналитическую СУБД для хранения и обработки данных.

## 2. Назначение компонентов

### 2.1. DuckDB

**Назначение:** локальная аналитическая обработка данных.

Основные задачи:

- Исследование новых наборов данных.
- Анализ структуры и содержимого Parquet.
- Выполнение SQL-запросов непосредственно к Parquet-файлам.
- Проверка результатов нормализации.
- Разработка и отладка аналитических запросов.
- Локальная проверка гипотез без загрузки данных в ClickHouse.

DuckDB не используется в качестве основного хранилища аналитических данных.

### 2.2. ClickHouse

**Назначение:** основная серверная аналитическая СУБД.

Основные задачи:

- Хранение аналитических таблиц.
- Обработка больших объёмов данных.
- Анализ истории орбитальных параметров.
- Выполнение агрегирующих и аналитических запросов.
- Обслуживание аналитических запросов через FastAPI.
- Предоставление данных для аналитических витрин.

ClickHouse является основным целевым движком аналитического слоя.

## 3. Архитектура взаимодействия

```text
CelesTrak / Space-Track
          |
          v
       Python
          |
          v
        MinIO
       Bronze
          |
          v
   PyArrow / Parquet
          |
          v
        MinIO
       Silver
          |
          +-------------------+
          |                   |
          v                   v
       DuckDB             ClickHouse
          |                   |
          |                   v
          |                dbt Core
          |                   |
          |                   v
          |               ClickHouse
          |                 Gold
          |                   |
          +                   v
                          FastAPI
```

### 3.1. Поток данных

1. Python получает исходные данные из CelesTrak и Space-Track.
2. Оригиналы сохраняются в MinIO в слое Bronze.
3. PyArrow выполняет нормализацию и формирует Parquet-файлы для слоя Silver.
4. DuckDB используется для локального исследования и проверки данных Silver.
5. ClickHouse получает необходимые наборы данных для аналитической обработки.
6. dbt выполняет преобразования и формирует аналитические витрины Gold в ClickHouse.
7. FastAPI предоставляет доступ к аналитическим данным.

## 4. Распределение ответственности

| Компонент | Ответственность |
|---|---|
| PostgreSQL | Метаданные, источники и история загрузок |
| MinIO | Хранение исходных и обработанных файлов |
| PyArrow | Нормализация и работа с Parquet |
| DuckDB | Локальная аналитика и исследование данных |
| ClickHouse | Серверная аналитическая обработка и хранение витрин |
| dbt Core | SQL-трансформации и построение моделей |
| Airflow | Оркестрация процессов |
| FastAPI | Предоставление данных через REST API |

## 5. Использование dbt Core

Для работы с двумя аналитическими СУБД предусмотрены отдельные адаптеры:

- `dbt-duckdb` — подключение dbt к DuckDB.
- `dbt-clickhouse` — подключение dbt к ClickHouse.

Основным целевым движком dbt является ClickHouse.

DuckDB может использоваться независимо от dbt для локальной разработки и проверки SQL-запросов.

При необходимости для DuckDB создаётся отдельный dbt-проект с собственным профилем и моделями.

Не следует предполагать полную совместимость SQL-моделей между двумя СУБД: синтаксис, функции и возможности материализации могут различаться.

## 6. Принципы использования

1. Исходные данные Bronze сохраняются без изменений.
2. Silver хранится в Parquet в MinIO.
3. DuckDB не заменяет постоянное хранилище Parquet.
4. ClickHouse используется как основная серверная аналитическая СУБД.
5. Аналитические витрины Gold формируются в ClickHouse.
6. PostgreSQL сохраняет ответственность за операционные данные и метаданные.
7. DuckDB и ClickHouse не должны независимо реализовывать одинаковые производственные процессы без необходимости.
8. Перенос данных в ClickHouse не должен приводить к потере исходных файлов в MinIO.

## 7. Развёртывание

Обе СУБД разворачиваются локально через Docker.

- ClickHouse работает как отдельный серверный сервис.
- DuckDB может использоваться непосредственно из Python-приложения без отдельного серверного контейнера.

Для локальной разработки допускается одновременная работа обеих СУБД.

## 8. Преимущества совместного использования

- Возможность локальной аналитики без дополнительной инфраструктуры.
- Работа с Parquet без обязательной загрузки данных в ClickHouse.
- Использование серверной OLAP-СУБД для аналитических запросов.
- Разделение исследовательской и производственной аналитики.
- Практическое изучение двух разных подходов к аналитическим вычислениям.
- Возможность развития архитектуры без отказа от существующего формата хранения данных.

## 9. Итоговая архитектурная концепция

В Orbital Data Platform DuckDB и ClickHouse выполняют разные функции и дополняют друг друга.

**DuckDB** — инструмент локальной аналитики, исследования и проверки данных.

**ClickHouse** — основная серверная аналитическая СУБД, используемая для построения и обслуживания витрин Gold.

MinIO и Parquet остаются основой Lakehouse-хранилища, PostgreSQL отвечает за метаданные, а dbt и Airflow обеспечивают преобразование и автоматизацию процессов.
